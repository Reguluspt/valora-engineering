## Context

ADR 0030 makes `ColumnMappingDecision` an append-only business fact and requires human confirmation before staging materialization. ADR 0046 makes the Project's explicit preliminary batch pointer and that batch's source-artifact pointer authoritative. G1.1G implements proposal, confirmation/correction, rejection and materialization commands with command-ID replay, but no persisted selection of one current mapping. Its model permits multiple proposals and multiple terminal decisions for the same source and structure. A read client cannot choose one by time, UUID, query order or browser state.

This ADR defines the missing selection authority. It ratchets ADR 0030 and ADR 0046 only for this boundary. It preserves ADR 0046's version and lineage selection for preliminary analysis and result: a later confirmation without a new materialized usage does not silently invalidate an existing analysis; D3 defines the consequence of a new selected materialization. It does not change S12 Apply v1, official `ProjectAssetLine`, canonical stages or Customer memory scope.

This ADR is accepted architecture authority. The F0 runtime candidate implements selection persistence, command changes, migration and a public recovery GET in one Macro PR. G1.1H Upload & Mapping UI remains unimplemented and blocked until that runtime is merged and exact-main CI succeeds.

## Decision

### D1. One explicit Project mapping authority slot

Maintain one tenant-scoped, versioned mapping authority slot per Project. Its key is `(organization_id, project_id)`. It records the selected current preliminary `import_batch_id`, `source_artifact_id`, `structure_snapshot_id`, the selected **human-confirmed** `ColumnMappingDecision.id`, and, when committed, the `ColumnMappingProfileUsage.id` that materialized that exact selection. A separate `current_staging_usage_id` in the same slot identifies the usage that owns the current batch staging rows; it may differ from the selected usage while a newer selection awaits materialization. The selected decision's sealed mapping snapshot identifies the candidate region and column roles; no separate candidate chosen from query order is authoritative. The slot has a monotonically increasing selection revision used as a CAS token for selection and materialization state. An absent/uninitialized slot is equivalent to revision 0 with no selection or proven staging owner; creation at expected revision 0 is serialized under the Project lock.

The slot is a mutable pointer/projection, not a replacement for append-only decisions or usages. Composite tenant, Project, batch, source and structure constraints must bind its references to the exact lineage. A NULL selected decision means **no mapping authority**, even if historical confirmations exist. A proposal, remembered profile, structure snapshot or Customer binding never fills the slot by itself. At most one confirmation is selected for the Project at a time, avoiding implicit reactivation when batches change.

The currentness predicate requires the slot's batch to equal `Project.current_preliminary_import_batch_id`, its source to equal that batch's `current_source_artifact_id`, an AVAILABLE source, a verified structure snapshot for that source, and a sealed accepted/corrected human confirmation on that same lineage. Any mismatch fails closed. A selected mapping is **materialized** only when its selected usage ID and the proven `current_staging_usage_id` are both non-NULL and equal, and that usage links to the exact selected decision and lineage. A structure snapshot's creation alone does not declare it current: a new snapshot becomes mapping authority only through selection of a human confirmation that references it. Reading a different snapshot never borrows the old selection.

### D2. Proposal and human decision boundaries

Multiple proposals may coexist as non-authoritative facts. One proposal may receive at most one new terminal human outcome: accepted/corrected confirmation **or** rejection. A future command checks existing terminal outcomes under the Project lock before appending one; a compatible tenant-scoped uniqueness constraint may supplement this only after legacy preflight. A new confirmation or rejection of an already resolved proposal conflicts; an exact committed command-ID replay still returns its original fact. Existing G1.1G history with contradictory outcomes is not rewritten and is handled under D7.

A successful new `ConfirmColumnMapping` or human correction that is authorized to become current both appends its decision and selects it in one transaction. The human request supplies the exact proposal/source/structure, expected selection revision, and command identity. The command validates active actor/tenant/RBAC, open Pre-case, explicit current batch and source, structure integrity, proposal lineage, selected roles, and Customer-memory permission. Neither deterministic rules nor AI can invoke human confirmation. A confirmation that loses the CAS race commits neither a decision nor selection nor success audit.

A subsequent valid confirmation may replace a selected confirmation before materialization. It leaves earlier decisions immutable, moves the explicit slot, clears its selected materialized-usage reference but retains the proven staging-owner reference until new materialization, increments the revision and writes one atomic success audit. There is no automatic newest-wins rule. Because G1.1G permits only one usage per `(organization, Project, batch, source, structure)`, once a usage exists for that lineage the slot may not move to a different confirmation on the same structure snapshot, even temporarily. An older materialized confirmation cannot be selected again after a different usage becomes staging owner; replay of its original command does not reactivate it. Correction after materialization requires a new verified structure snapshot and a new proposal/confirmation, or a separately approved versioned-rematerialization contract. This ADR does not silently relax the existing usage uniqueness constraint.

Rejecting a proposal appends a rejection only for that proposal. It does not clear or replace an already selected confirmation, remove staging, or change a materialized usage. Clearing selection, if ever needed without replacement or lineage change, requires a separate explicit audited human command with expected revision. Rejection is not that command.

### D3. Materialization and staging lineage

`MaterializeConfirmedMappingToStaging` may commit only for the slot's selected confirmation on the exact current batch/source/structure and expected selection revision. Under the accepted Project → batch lock order, it rechecks that selection before committing staging, usage, selected usage identity, `current_staging_usage_id`, an incremented slot revision and one required success audit atomically. The two usage IDs then equal the newly committed usage. A prior usage is historical and cannot prove current staging after the staging-owner marker moves. Repeating the same committed command ID returns its committed usage without a second staging mutation, authority change, revision increment or success audit, even if current authority later moved.

Selecting a different confirmation before materialization, or on a new structure snapshot, does not rewrite staging. Until that selection is materialized, the read projection says selected mapping is **not materialized**; an older usage may still own physical staging through `current_staging_usage_id` but is not presented as the selected mapping's result. A later new materialization may replace staging through the existing staging-only boundary. Existing staging rows do not identify their producing usage, so the runtime must persist and maintain this owner marker before claiming a selected usage materialized current staging. Every other path that replaces, deletes or remaps current-batch staging must compare the expected selection revision, clear the staging-owner and selected materialized-usage references, increment the revision, and record the ownership change in its one success audit atomically under the same Project/batch lock, or be closed for a selected lineage; a stale marker never proves ownership. If the selected confirmation's source/structure already has a usage, marker clearing leaves it selected but **recovery required**, not eligible for rematerialization under the same uniqueness key. Recovery requires a new verified structure snapshot, proposal, human confirmation/selection and materialization, or a separately accepted versioned-rematerialization contract. This ADR does not invoke or alter Apply v1 and never promotes `ProjectAssetLine`.

An unmaterialized new selection does not by itself change ADR 0046's current analysis/result or block Official Intake based on an otherwise current result; the read projection must show that the selected mapping has not produced that analysis. Once a new selected usage materializes, an analysis whose embedded decision/usage differs from that selected usage, and a result that references such an analysis, are no longer current for further Pre-case work or a new Official Intake commit. Clearing the staging-owner marker after a non-mapping staging mutation likewise makes analysis/result on the displaced usage non-current for a new Intake. After either invalidation, a recoverable selected mapping must materialize, or a new verified snapshot and confirmation must establish one, then a new analysis/result must be explicitly generated on its usage before Intake. Previously committed Official Intake facts remain frozen. If a legacy Project has no selection slot yet, its already committed analysis/result remains under ADR 0046 currentness until new selected materialization; D7 governs remediation of its mapping history.

### D4. Batch, source, structure and Official Intake changes

An audited current-batch switch or a successful source-generation replacement invalidates the slot in the same authoritative transaction: clear selected lineage, selected usage and `current_staging_usage_id`, increment its revision and retain old decisions/usages as history. A switch back to a formerly current batch does not resurrect an old selection. No mapping memory or proposal carries authority into a new batch or source. Until the clearing integration is implemented, any read or command seeing a pointer mismatch must fail closed and must not report the old selection as current.

A newly created structure snapshot for the **same** current source is an alternative immutable candidate, not an implicit replacement. The selected old snapshot remains selected until an explicit confirmation selects a new one; reads for the new snapshot show no selected mapping. If the selected snapshot fails integrity verification, authority is unavailable until an authorized remediation; do not substitute another snapshot by version or order. A batch/source change always invalidates it under the preceding rule.

After Official Intake, no new proposal, confirmation, rejection, selection or materialization is permitted. Historical reads and true replay of already committed command IDs follow G1.1G access and replay rules. The Official Intake fact and prior analysis/result lineage remain immutable.

### D5. CAS, atomicity and replay

The selection revision is the mapping authority CAS token. It increments on selection, materialization, batch/source invalidation and staging-owner clearing; true replay and read do not increment it. Mapping selection/materialization and other staging writers that alter its markers supply the expected selection revision and exact batch/source/structure identities where applicable. A batch switch or source replacement retains its existing Project row-version or expected-source CAS and clears/increments the slot under the same locks; it need not add a second caller-supplied CAS token. Lock Project, then current batch, then the selection slot and dependent mapping facts in a consistent order. Validate active user and organization, tenant scope, current pointers and version under that lock. If another command changed authority first, return a conflict; the caller must read again, and any human confirmation requires a new explicit decision. Do not silently retry against refreshed authority. The selection revision governs mapping changes and is not a second Project lifecycle state machine.

Confirmation and selection are one commit: append-only decision, pointer update/revision and one required audit either all commit or all roll back. Materialization follows D3's atomic boundary. A durable command identity and canonical request digest distinguish a true replay from key reuse. After fresh authentication/authorization, replay returns the original committed decision or usage without reapplying a stale pointer, incrementing revision, or duplicating audit. New commands after Official Intake remain closed. Exact replay semantics must be implemented before changing G1.1G command payloads; a rejected or ambiguous response must be recoverable through read, not by issuing a new command ID.

### D6. Customer memory is separate

`ColumnMappingProfile` memory may prefill a proposal but never becomes selected mapping authority. An unbound Pre-case Project can select a human-confirmed mapping with `memory_scope=none`; it cannot create Customer-scoped memory. Historical NULL Customer snapshots are not restamped after binding. Binding does not select, clear or rematerialize mapping. Customer memory choices remain those of ADR 0030 and ADR 0046.

### D7. Legacy G1.1G facts and migration

Migration preserves every decision, profile, usage, audit event and staging fact. It creates no selected mapping from history automatically. For direct legacy selection, **eligible** means a verified human accepted/corrected confirmation on the exact current batch/source/structure lineage whose source/structure usage uniqueness key is still unoccupied and whose proposal has no contradictory terminal outcome; a materialized historical confirmation is not eligible for direct selection. For zero eligible confirmations, the slot is NULL/revision 0; proposals, rejections and any ineligible confirmations remain readable as history, but no confirmation is selected. For one eligible confirmation, authority is still unresolved until an authenticated human explicitly selects that exact fact under CAS and audit. For two or more eligible confirmations, there is likewise no inferred winner; explicit audited remediation identifies the intended eligible confirmation and verifies its exact current lineage. A proposal with contradictory terminal outcomes cannot be directly selected; recovery requires a new verified structure snapshot, proposal and human confirmation, or a separately accepted repair contract. Corrupt or cross-tenant facts are never selectable. A new database constraint must not require deleting or rewriting contradictory legacy rows.

An explicit legacy-selection command may bind an **eligible** unmaterialized historical confirmation without creating another decision or Customer memory. A legacy usage row alone does not prove that it still owns batch staging, because later materializations may have replaced it; migration leaves `current_staging_usage_id` NULL and this ADR authorizes no automatic or manual attachment of an old usage to the new slot. Where a usage already occupies the source/structure uniqueness key, the safe v1 remediation is a new verified structure snapshot, proposal, human confirmation/selection and materialization, which establishes the staging-owner marker. A non-mapping writer may not replace current-batch staging while legacy ownership is unresolved; it first requires remediation or a separately accepted currentness-invalidation contract. A different repair path would need a separately accepted provenance contract. No timestamp, highest UUID, sole-row shortcut or browser-held ID substitutes for that proof.

This conservative bootstrap does not retroactively invalidate previously committed Preliminary Analysis/Result or Official Intake facts. Analysis/result currentness remains governed by ADR 0046's verified materialized lineage, with D3's additional match to a newly selected materialization. The new mapping slot governs future mapping work and recovery; it is not a rewrite of historical case-state decisions. Downgrade must refuse if selection authority cannot be represented without losing or fabricating facts.

### D8. Public read consequence and runtime gate

Once the persistence and commands exist, one authenticated Project/batch-scoped read projection can expose: current Project batch and source IDs; selection revision; selected confirmation ID, outcome, exact structure snapshot and candidate lineage, sealed mapping snapshot/digest, memory scope/profile ID; selected materialization usage ID/count/digest or NULL; current staging-owner usage ID or NULL; and a bounded, explicitly scoped set of proposal/decision statuses needed for recovery. It must distinguish no selection, unresolved legacy history, selected but unmaterialized, selected but recovery required, materialized, stale lineage and closed Official Intake. `Materialized` requires the two usage IDs to match and verify; a historical usage alone cannot produce that status. If analysis/result lineage is included, it must say whether it uses the selected materialized usage, without implying that an unmaterialized selection generated it. It must not expose storage keys or cross-tenant facts. The selected decision and usage come from the slot and verified links, never from array order.

ADR acceptance and merge alone did **not** create this read state. The F0 runtime task implements the pointer, migration, commands and read contract in one candidate. The Upload & Mapping UI remains blocked until the runtime candidate is merged and exact-main CI succeeds.

## Options considered

| Option | Decision | Reason |
| --- | --- | --- |
| Latest-created confirmation wins | Rejected | Hidden authority depends on time/order and cannot prevent lost updates. |
| Highest UUID or database identity wins | Rejected | Identity is not a business selection or concurrency rule. |
| Frontend retains the chosen decision | Rejected | Refresh, another device and lost responses cannot recover server authority. |
| Infer authority from materialization | Rejected as primary rule | Confirmation needs recoverable authority before materialization; old usages may not own current staging. |
| Explicit versioned Project mapping slot | Chosen | One auditable selection with CAS, exact lineage and deterministic recovery; requires a bounded persistence/command migration. |
