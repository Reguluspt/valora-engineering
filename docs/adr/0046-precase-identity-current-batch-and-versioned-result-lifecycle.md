# ADR 0046 — Pre-case Identity, Current Import Batch, and Versioned Preliminary Result Lifecycle

**Status:** Accepted design authority (Product Owner decisions D1–D3); G1.1 runtime not started
**Date:** 2026-09-27
**Scope:** OS-G1 Pre-case through the first Official Intake commit
**Decider:** Product Owner

## Context and authority relationship

The Product Owner approved three linked decisions: a Pre-case may have no Customer; Project has an explicit current preliminary import batch; and immutable preliminary analysis/result facts may be regenerated before Official Intake. One ADR keeps their identity, lineage and freeze rules together. This ratchets ADR 0030's mapping-memory scope, ADR 0037's stable Project and append-only Official Intake fact, and ADR 0038's current-source and current-artifact predicates. It does not replace their human confirmation, source integrity, stage vocabulary or blocker rules. Where PR-01 contracts and the G1.0 provider currently require exactly one snapshot or result per Project, that is the implemented v1 limit; this ADR defines the future G1.1 target and does not make current runtime compliant by declaration.

This is design and migration authority only. No model, migration, service, API, UI, test, dependency or deployment change is authorized by this ADR alone. Each runtime slice requires its own implementation packet and acceptance evidence.

## Decision D1 — Project identity and optional Pre-case Customer

`Project.id` is the stable case identity from Pre-case through Official Intake and the official dossier. `Project.customer_id` may be NULL during Pre-case. A Customer is not required to create the Project, upload `.xlsx`/`.xls`, confirm mapping, finalize analysis or generate a result. No dummy/placeholder Customer, silent Customer creation, second Project or cloning at Official Intake is permitted.

The first successful `CommitProjectOfficialIntake` requires that the **same** Project is explicitly bound to a real, ACTIVE Customer in the same tenant. Customer binding is not an intake side effect. The accepted command boundary is `BindPreliminaryProjectCustomer`:

1. An authenticated, authorized human supplies tenant, Project, real Customer, expected `Project.row_version`, bounded idempotency key and canonical request digest. Lock Project, then validate Customer's tenant and ACTIVE status within the transaction. A missing or cross-tenant resource is denied without disclosure.
2. Only NULL → that Customer is permitted. CAS failure, an existing different Customer, inactive Customer, post-Official-Intake attempt and conflicting key/digest fail closed. A same-Customer retry with the same request is a deterministic `ALREADY_BOUND` replay, subject to fresh authorization, with no second success audit or version increment. Rebinding is outside this lifecycle.
3. The success transaction changes only Project's binding and version and appends exactly one audit event containing actor, Customer, old/new Project versions and request identity. Failure rolls back mutation and success audit. Project ID remains fixed.
4. Binding does not regenerate mapping, analysis, result, staging or `ProjectAssetLine`, nor change an existing fact's `customer_id`. Historical NULL is a truthful snapshot of the unbound time. Subsequent operations may use customer-scoped mapping memory, after the ordinary human confirmation gates.

Before binding, customer-scoped mapping retrieval and creation of customer-scoped reusable memory are unavailable. Approved organization-level templates and new deterministic mapping remain eligible under ADR 0030; confirmation is still required. An unbound mapping decision records `memory_scope=none` and may use an applicable `organization_template` profile; those are distinct fields/enums, and neither creates a fabricated Customer. Existing `ColumnMappingProfile.source_customer_id` may remain required for profiles sourced from a bound Project; this design does not authorize creating a reusable source profile from an unbound Project.

For immutable Pre-case facts that currently store `customer_id`, its target meaning is **nullable snapshot metadata at fact creation**, not a live equality constraint with `Project.customer_id`. The tenant, Project and exact source/decision/usage lineage remain mandatory. Existing non-NULL history is preserved. Future removal of snapshot columns would need a separate versioned contract. Downstream official asset-identity and dossier facts continue to require a bound Customer.

## Decision D2 — Explicit current preliminary import batch

Add nullable `Project.current_preliminary_import_batch_id`. Its composite FK uses `(organization_id, id, current_preliminary_import_batch_id)` to reference `(organization_id, project_id, id)` on `ProjectAssetImportBatch`. The batch's `current_source_artifact_id` continues to select its source generation. The authoritative chain is Project → explicit batch pointer → batch's explicit source pointer → source generation. NULL means no established current batch, **not** permission to infer one from timestamp, UUID, row count or a sole query result.

- A Project may begin without a workbook or batch. Creating its first active batch sets the Project pointer in the same transaction after inserting the batch.
- Re-upload/replacement **within the same intake** changes that batch's source-generation pointer. The batch pointer remains fixed; analyses/results tied to the former source become historical.
- A genuinely restarted intake creates a new batch, then an explicit `SwitchCurrentPreliminaryImportBatch` command sets the Project pointer. The command requires authenticated tenant/RBAC scope, expected Project version, expected old pointer, idempotency/digest, a same-Project target batch, Project lock, atomic version increment and one success audit. Historical batches/source facts remain. A same-request retry returns the committed outcome; stale/conflicting requests fail closed.
- Once an Official Intake fact exists, switching is closed. No post-commit reopening is designed here. Project lock order serializes the switch with Official Intake. The latter must recheck the pointer and source after acquiring locks.
- A batch pointer switch or source-generation replacement invalidates downstream currentness by lineage without rewriting prior snapshots or artifacts.

## Decision D3 — Immutable versioned analysis and result

`PreliminaryAnalysisSnapshot` and `PreliminaryResultArtifact` are immutable facts with positive, Project-scoped monotonically increasing versions. Existing unique `(organization_id, project_id, version)` constraints remain the last defense against duplicate claims; idempotency constraints remain. Historical rows stay queryable and do not themselves create ambiguity. A version is never reused, including after invalidation. Missing/corrupt lineage fails closed.

**Current analysis.** Among finalized, checksum/digest-valid snapshots for the Project, choose the highest version whose exact lineage matches the Project's explicit current batch, the batch's current AVAILABLE source generation, accepted structure/mapping decision, and the **materialized** `ColumnMappingProfileUsage` and its digests. A later confirmation that has not materialized a new usage does not silently invalidate a snapshot. If no such snapshot exists, `PRELIMINARY_ANALYSIS` is `INCOMPLETE`. Two legitimate same-version claims are an integrity failure (`NOT_AVAILABLE`), prevented normally by the unique constraint. Never choose by timestamp or query order. ADR 0038's line completeness and blocker rules still apply.

**Current result.** Among finalized, immutable, checksum/manifest-valid artifacts for the Project, choose the highest artifact version whose lineage references the **selected current analysis** ID, version and digest and matches its source lineage. The existing result fact carries those analysis references in `lineage_manifest` JSON rather than structural analysis-ID/version/digest columns; the future provider must validate the manifest fields against the selected snapshot and its digests, failing closed on absence or mismatch. This design does not require new structural result columns. If no matching artifact exists, `PRELIMINARY_READY` is `INCOMPLETE`. An older result tied to an older analysis is historical, not current. Multiple valid historical versions do not cause `NOT_AVAILABLE`; an actual same-version conflict or corrupt evidence fails closed. There is no readiness table or `current_result_id` pointer. The provider computes both selections from facts under a consistent read.

**Regeneration command.** A future explicit human-confirmed `GeneratePreliminaryResultVersion` accepts tenant/Project, expected Project version, selected current analysis ID/version/digest, bounded idempotency key and request digest. It requires authorization, an uncommitted Pre-case, current validated lineage and checksum-verified generated bytes. Allocate `max(version)+1` under `Project FOR UPDATE`; enforce unique `(organization_id, project_id, version)` and `(organization_id, idempotency_key)`. A deterministic immutable storage key plus the committed artifact's idempotency identity permit lost-response replay without a second version. If byte generation runs outside the lock, finalization reacquires Project lock, rechecks every expected pointer/analysis/source and either inserts fact plus one audit atomically or discards the candidate bytes without authority. A concurrent loser retries against newly selected state or returns a conflict; it cannot publish the same version. The same pattern governs future finalized analysis successors. No generation occurs as an invisible effect of Customer binding, batch switching, source replacement or Official Intake.

## Official Intake and terminal Pre-case disposition

`CommitProjectOfficialIntake` uses the same Project, verifies a currently ACTIVE same-tenant bound Customer and **current** applicable result, and freezes exactly `PreliminaryResultArtifact.id`, version, content SHA-256 and `source_snapshot_sha256` in its one append-only fact. Artifact snapshot `customer_id=NULL` is valid when it was generated before binding; currentness uses tenant/Project/lineage, not equality to today's Project Customer. The command retains G1.0's source-currentness validation, deterministic lock order, expected versions, idempotent replay and atomic fact/audit behavior. The commit fact's Customer is non-NULL and records the bound legal identity at commit. Later Customer status changes do not rewrite it. After commit, no new Pre-case result or current-batch switch is allowed; the same Project proceeds to the official dossier.

`Không tiếp tục` remains an explicit human terminal Pre-case disposition, not a canonical Case Stage. It blocks Official Intake and new Pre-case generation/switching under this lifecycle, retains Project/source/analysis/result/audit history and offers `Xem lịch sử`. Its future persistence/command is a separate slice. The superseded customer-response states (`Ghi nhận đã gửi`, `Chờ khách hàng phản hồi`, `Ghi nhận phản hồi`, `Đã chấp thuận giá đề xuất`) are not restored. The path is result creation → explicit Official Intake → `Tổng quan hồ sơ`; customer agreement occurs outside VALORA.

ADR 0030 already requires `.xlsx` and `.xls` for Adaptive Intake v2. Selecting and security-reviewing a legacy `.xls` parser is a later implementation gate; this ADR adds no dependency.

## Migration impact matrix (design, no migration executed)

Legend: `NN` = NOT NULL; `N` = nullable; `—` = no column. Every upgrade preserves existing values and checks all orphan/cross-tenant rows before constraint changes. Every downgrade is a **preflighted refusal** if target v1 cannot represent current data; never delete or forge immutable facts to make it fit. “Runtime” describes the required future compatibility work, not work completed here.

|---|---|---|---|---|

In particular, replace `column_mapping_decisions`' current Customer-bearing lineage unique target with a unique `(organization_id, project_id, import_batch_id, source_artifact_id, structure_snapshot_id, id)` target. Repoint its self-reference to `proposal_decision_id`, the usage confirmation FK and the analysis decision FK to that target. Keep the existing usage generation uniqueness (which already excludes Customer). A nullable Customer may never be the sole path that proves a proposal, confirmation or analysis belongs to the same tenant/Project/source generation. Add the artifact `(organization_id, project_id, id)` unique target before changing the Official Intake artifact FK. PostgreSQL's default `MATCH SIMPLE` would otherwise allow NULL Customer to bypass the whole old composite reference. Validate old rows and install new nonnullable lineage FKs before dropping old constraints.

For legacy Projects with multiple batches and no unique immutable lineage evidence, the pointer stays NULL and Case State is unavailable for current-batch-dependent stages until an authenticated, audited remediation selects a verified batch. A committed case's append-only commit remains historical truth even if a legacy pointer anomaly is unresolved; normal Pre-case switch is forbidden, so a separate remediation contract is required. Migrations must not silently choose a batch or rewrite a committed result. A rollback is blocked if any unbound Project/fact, multiple versions, or pointer semantics cannot be represented by v1; it is not a destructive downgrade.

## Case State truth tables

These rows assume no separate open BLOCKING ValidationIssue. If one applies to an incomplete stage, ADR 0038 promotes that stage to `BLOCKED` and blocker resolution takes Next Action precedence. `NOT_AVAILABLE` denotes corrupt/ambiguous evidence or provider failure, never merely old valid history. Stage completion still follows ADR 0038's contiguous-prefix projection. “Current” below is the relevant fact selected by these rules, not a new table. Commands are future contracts unless already implemented.

## Required G1.0 and PR-01 implementation deltas for later slices

The G1.0 gate's fail-closed intent remains. Its current provider's `len()==1` checks for batch, analysis and artifact and `amb1` multiplicity outcome must become pointer selection plus highest-valid-version selection; corrupt duplicate claims remain unavailable. The result generator's one-artifact-per-Project application gate and analysis generator's one-snapshot-per-Project gate must become serialized version allocation. `official_intake_service` must stop requiring `artifact.customer_id == project.customer_id`, require an ACTIVE bound Customer independently, and compare exact selected result/analysis/source lineage under the Project/batch locks. Customer-bearing mapping/usage equality checks must use historical nullable snapshot semantics. Project creation, API schemas, authorization joins, mapping retrieval, result manifest, tests and error codes must be revised in bounded runtime slices. Existing replay and exact-source checks may not regress. No such code change is made in this authority task.
