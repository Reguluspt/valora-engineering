Disable/retire legacy per-line POST as a current official writer in the future authorized cutover; no legacy route may write successor heads, create an official receipt, or satisfy selection COMPLETE. Existing historical regression tests remain relevant only to retained history.

Later migration proof must cover upgrade from the current single Alembic head, isolated downgrade/re-upgrade, composite FK and append-only SQL/ORM enforcement, exact decimal extremes, and byte-for-byte legacy history parity. No automatic legacy promotion. Downgrade with populated successor journals must refuse destructive data loss; empty-schema round trips are tested separately from a documented retention/backup recovery plan. This ADR supplies no SQL or migration.

## 3. Project commercial basis and deviation-only prerequisite

### 3.1 Three explicit declarations

Propose immutable `ProjectCommercialBasisRevision` plus one scoped current pointer. Its positive revision contains exactly three explicit booleans: `vat_included`, `transport_included`, `installation_labor_included`; tenant/Project; version/policy `project-commercial-basis-v1`; predecessor; authenticated actor; server UTC; originating create/change command UUID/receipt/audit; and canonical content digest. No null/default-false substitution is allowed. Absence of a basis revision means unknown, not three NO values. A basis revision is professional Project metadata, not a supplier's promise or a price transformation.

Future ProjectCreate accepts all three declarations through the existing creation action and `project:create`, active same-tenant human and atomic create audit/receipt; it requires no pre-existing Workbench session for a Project that does not exist yet. Persist basis revision 1 with creation, or roll back creation together. Existing projects remain absent/unknown until a separately authorized explicit declaration path is used; no automatic migration/backfill. Proposed subsequent `ReviseProjectCommercialBasis` (including first explicit declaration on a legacy Project) uses `workbench:edit`, active owned session, DRAFT, expected Project/shared Case State/basis revision, UUID and atomic receipt/audit. It appends a successor, never edits prior declarations, and rejects a no-op. Generic Project PATCH must not bypass that boundary. Non-DRAFT change/reversal policy remains unauthorized; historical reads are allowed.

Changing a boolean or establishing a previously missing basis is material to every positive selection prepared under the prior basis/absence marker. It invalidates those heads through §7 and shared CAS, without editing quotation facts or auto-selecting replacements. Merely changing unrelated Project metadata does not stale selections. Newly recorded basis does not rewrite what earlier quotations claimed; PO presumption is identified explicitly by policy/version and current Project basis in preparation/history.

### 3.2 Controlled deviation journal

Propose additive `SupplierQuoteCommercialDeviationFact` and a scoped fold/index alongside, not inside, immutable A13 quote facts. Record **only discovered deviations and their correction/clear history**. No row is required to affirm normal compliance; no per-quotation checkbox, upload, extra confirmation or positive proof is required. Future optional `RecordSupplierQuoteDeviation` / `CorrectSupplierQuoteDeviation` / `ClearSupplierQuoteDeviation` are authenticated professional metadata commands under existing `workbench:edit`, active owned session and DRAFT. Their existing action records the change once; no additional approval step. No AI/system detection or inference from free text.

Each immutable fact records organization/Project, logical quote DocumentRecord, exact quote revision, explicit affected effective item IDs (or all items in that exact revision), exact line bindings, Project-basis revision at observation, one or more of the three axes, actual discovered inclusion YES/NO for those axes, predecessor/corrected fact, bounded protected reason, actor/session/UTC, command/receipt/audit and content digest. The initial record must actually differ from the referenced Project declaration on at least one named axis. No price amount/allocation or warranty/payment/delivery-timing comparison field belongs in this journal. Correction appends a replacement factual declaration; clear appends the exact targeted closure and reason, never deletes the earlier fact. Require exact deviation-head generation in CAS; a clear cannot target another quote, unknown head or unrelated basis.

Applicability is resolved from exact quote lineage and items, not Supplier name. Within the same quotation revision, retained actual-inclusion facts are compared with the current Project booleans; a new Project basis does not silently erase known facts. The old observation's basis remains historical provenance. A new basis can make a formerly deviating actual inclusion match, but this never restores old official selection currentness: the basis change is material and retained invalidation remains sticky. If applicability cannot be resolved, ranking fails closed for affected candidates.

A correction/replacement/negotiation successor cannot silently drop a known unresolved deviation. The future A13 revision adapter carries an explicit prior-deviation lineage reference; matching exact lines retain the recorded actual inclusion until a targeted human correction/clear supplies new facts. Omitted items have no current candidate; ambiguous remapping is excluded from automatic ranking, never guessed. This is negative-history continuity, not automatic confirmation of the successor or a new mandatory affirmative attestation. An explicit clear is needed only when correcting a previously recorded deviation, never for normal quotations.

A deviation changes ranking metadata, not A13 source-confirmed terms or eligibility. An otherwise eligible deviating item remains deliberately selectable with the difference visible. Newly discovered/corrected/cleared **applicable selected-item** deviations materially change a positive selection's comparison/provenance and invalidate it; later clear does not revive that head. Changes only to an unselected offer refresh suggestion/CAS, not an unchanged official choice. All future basis/deviation writers use Project-first locking, the shared token, append-only receipts/audits and the same invalidation writer (§7); no independent token. Failures roll back their own metadata transaction. Their effects must be folded into coherent authority before selection runtime is enabled.

**Prerequisite gate:** ProjectCreate/basis lifecycle and the A13 deviation/lineage adapter are future separately authorized Authority → Runtime → Product Closure slices, not changes implemented or tasks created by A17. Their detailed physical storage/commands remain ADR recommendations pending PO architecture acceptance. Selection runtime DoR cannot claim them satisfied until certified. They preserve current A13 free-text history and its original confirmation receipt; no old A13 digest is retroactively changed.

## 4. Exact A13 selection and server ranking

### 4.1 Candidate and currentness closure

Resolve candidates through the same canonical A13 fold. Bind organization + Project + exact nonempty sealed membership/order/STT + line/version/content digest; logical quote DocumentRecord; contributing registration/revision fact ID and revision number; exact contributing confirmation fact and receipt/audit; effective SupplierQuoteItem ID **and its owning `fact_id`**; confirmed effective item-set digest; Supplier tenant/ID/version/material binding; currency/unit identities; current source DocumentRevision/StorageObjectBinding/head generation and verified-byte proof; upstream PRICE_EVIDENCE closure; and Project basis/deviation policy/generations or explicit absent-basis marker.

An item owner may be registration/revision or a later draft line-registration fact; it is not necessarily the revision or confirmation. Verify the confirmation's `confirmed_items` against the folded effective item set. Latest negotiation draft and contributing confirmed revision are separate invocation facts. A negotiation draft alone preserves the confirmed predecessor; correction/replacement withdraws it, and confirmed successor supersedes its entire item set including omitted lines. Rejecting an optional draft can preserve the contributing predecessor. Withdrawal/rejection/supersession never permits older-revision fallback.

Every selected item must be A13 eligible, same exact line, effective and unexpired, with active resolved/unmerged/unambiguous Supplier, intact source and journal. Project-global A13 journal integrity and applicable concerns cannot be narrowed to selected rows. Whole-quote line-binding closure remains A13's actual scope. No legacy QuoteLine/EvidenceFile fallback, automatic quote confirmation, fuzzy identity or canonical fan-out. Warnings do not remove eligible candidates. Optional stale unselected offers need not stale selection if selected closure and A13 COMPLETE remain intact; global integrity/known concerns still prevail.

Source proof preserves exact document/revision/head generation, checksum, byte length, binding/profile/container identity, provider object version/creation identity and before/read-verified/after observations. `retained_source` already enforces a 32,000,000-byte per-object bound and same-generation checks. No remote fallback, same-ID byte swap, parsing/OCR or source-content attestation is added. Storage targets stay protected; public views expose safe IDs/digests/reasons, not keys/paths/URLs or bytes.

### 4.2 E1-B automatic suggestion

For each exact line, server preparation resolves the **full eligible candidate set**, not a page. Its automatic comparison group contains only candidates with known compatible exact line basis, positive finite Numeric(26,8)-compatible unit price, exact sealed quantity/unit, resolved identical comparison currency, current A13 proof, complete Project three-axis basis, and no applicable deviation under `project-commercial-basis-v1`. Compatibility uses the authoritative line/currency/unit bindings, never conversion or browser arithmetic. A13 warning `same_working_unit_basis` is not an added requirement for PO-B commercial presumption or a replacement for exact money/unit checks. Working price may be absent while candidate-to-candidate ranking remains possible on a proved common currency/unit/quantity basis.

Known deviating candidates are excluded from the automatic group but stay visible and deliberately selectable if A13 eligible. Other eligible candidates whose money/unit/quantity/line basis cannot be placed on the same exact comparison basis cause UNRANKABLE rather than a purported global minimum over an arbitrary currency/unit subset. This preserves the resume contract’s explicit monetary/unit-comparability-failure rule and A15’s no-arbitrary-incomparable-group rule; PO-B authorizes commercial-deviation exclusions, not a currency preference or conversion policy. When a non-deviating compatible group exists and every other eligible offer is excluded specifically for a known commercial deviation, label the suggestion as lowest **on the declared Project basis**, disclose exclusions, and do not claim it is an adjusted overall minimum. Missing Project declarations, unprovable monetary/unit basis or an empty comparable non-deviating group returns **UNRANKABLE**, with no fabricated default. A single safely comparable non-deviating offer suffices; no mandatory-three rule.

Compare unadjusted exact Decimal unit prices. No VAT gross-up, transportation allocation, installation adjustment, FX, unit/quantity conversion or commercial normalization. Warranty, payment and delivery timing remain retained A13 context and any existing A13 eligibility rules, but are **not ranking equivalence gates**. Presumption provenance says PO-authorized assumption, never supplier-attested documentary compliance.

Use `supplier-selection-ranking-v1`: exact Decimal minimum; expose every equally low item; order ties by canonical lowercase UUID tuple `(supplier_id, quote_id, revision_fact_id, item_id)` and propose the lexicographically first. Persist policy version, full candidate/group/exclusion digest, tie members/order and chosen origin. No hidden supplier preference or extra tie click. Protected preparation displays ties, declarations/deviations, safe source lineage and exact decimal text.

Preparation origins distinguish system suggestion, deliberate override/unrankable choice, existing official retention and stale successor. Where a safe suggestion exists, no manual pick is required. Otherwise deliberate choice of an eligible item is required before the single whole-set CTA. A current official head stays the prepared choice despite a newer cheaper offer; show fresh suggestion separately. Background refresh never replaces reviewed choices or official heads. A changed preparation invalidates submission and requires refreshed review, not silent substitution.

### 4.3 Precision and warnings

Persist prices/quantities as Numeric(26,8), Decimal in domain, decimal strings in JSON/UI. Reject floats, NaN/Infinity, excess scale/range; display rounding never changes stored values or comparisons. Difference requires at least Numeric(27,8); derived percent uses explicitly recorded Decimal context/rounding only for display. Threshold uses exact multiplication, never rounded percent.

Reuse/extract A13 `comparison_warnings` as the one canonical comparator with regression parity. For comparable working C > 0 and quote S: below when S < C; strict deviation when `abs(S-C)*100 > C*15`; exactly 15% does not trigger the latter. Preserve both codes when applicable. NULL/zero/incomparable working reference retains current A13 semantics: no fabricated percentage or warning; do not introduce a different zero-price algorithm. Current A13 converts stored working values with `Decimal(line.appraised_unit_price)`; preserve and disclose that legacy provenance, not a claim of recovered original precision. Warnings stay nonblocking, acknowledgement optional, and never set final appraisal price.

Current pointers/monotonic counters are mutable indexes validated against immutable chains. No persisted Case State/COMPLETE flag.

Corrupt history/observation journals fail closed and cannot be repaired or waived by a successor. Every FK deletes RESTRICT; historical records are not garbage-collected as part of this design.

## 6. Whole-set professional command, receipt and security

### 6.1 Preparation and the single action

`ConfirmSupplierSelectionSet` is the only proposed positive write for first/change/reconfirm/re-establish. One click on **“Xác nhận danh sách NCC đã chọn”** submits one Project-scoped complete ordered manifest and `confirm: true`. No per-line confirm flags/buttons, second approval, modal/checklist, extra attestation or automatic submission. Preparing/editing a row is not a commit. Server preparation binds tenant/actor/session, Project row version, shared v7 case token, seal/set/membership, every line version, A13/upstream closure, basis/deviation generations, full candidate/group/tie/exclusion digest, proposed and original tuples, policy versions and expiry. Return a server-authenticated bounded preparation envelope/digest; server recomputes it at commit. It is non-authoritative and expires when its dependencies change; no preparation table is a completion fact.

The request includes one stable UUID/contract, preparation envelope, expected Project row version **and** shared Case State token, exact seal/member order/digest, full line-version set, owned session, upstream confirmation, and each line's chosen exact tuple, expected head/revision/predecessor/invalidation generation, operation/context and origin. For deliberate choice, carry the user's chosen item distinct from the server's suggested/original tuple; validate eligibility and permitted provenance server-side. Client-supplied origins/prices/Supplier snapshots are never proof. Unrankable rows lacking a retained current official choice require explicit chosen IDs, not fabricated defaults. No extra acknowledgement is added.

Compare manifest set and order exactly to the inherited sealed set, including offscreen/paged/virtualized rows; reject duplicate, omitted, foreign or reordered members. Pagination affects display/receipt retrieval only. Changed preparation/candidate authority conflicts; never recompute a new cheapest item and commit it in place of the reviewed tuple. UI can preserve local edits only as uncommitted proposals for new review.

| Server-resolved row effect | Immutable outcome |
| --- | --- |
| `first` | Absent head/revision 0 → positive revision 1 with full source/provenance. |
| `change` | Current positive predecessor → new item/choice successor; same Supplier with another item still changes. |
| `reconfirm` | Stale positive predecessor → successor bound to latest invalidation generation and freshly eligible chosen tuple; same item allowed only if eligible now. Stale predecessor cannot be retained. |
| `re-establish` | Exact tombstone predecessor → positive successor; revision numbers never reset. |
| `retain` | Exact unchanged current positive head remains untouched; receipt member references original revision and provenance, no new line confirmation audit. |

Classify stale positive replacement as reconfirm with chosen-change context rather than hiding invalidation in `retain`. Entirely unchanged new invocations are redundant and rejected; same-UUID replay returns the original result. A newly cheaper option alone changes neither official head nor retained human provenance.

`WithdrawSupplierSelectionSet` is separate negative authority: one explicit target set, potentially a subset of sealed lines, exact positive predecessors (including stale), reason/context and shared CAS. Append tombstones atomically for all targets, keep heads/history and increment revisions. It needs intact correspondence/history but not current eligible quote or positive upstream COMPLETE. No physical deletion, older-head fallback or false positive full-set receipt. It uses the same human/session/DRAFT security and uncertainty protocol, not a per-line positive confirmation sequence. Corrupt history or unresolved membership denies withdrawal rather than hiding it.

### 6.2 Transaction and final currentness boundary

One caller-owned outer PostgreSQL transaction owns all positive effects. Services never commit children/audits independently. Acquire same-tenant Project FOR UPDATE first, then active actor/org/grants/owned session and the canonical dependency path (§8). Reload after waits; check DRAFT, exact invocation versions, intact upstream/A13/basis/deviation/selection/observation journals, complete membership and every chosen item including retained rows. Resolve row effects before writes. Any invalid row, stale retain, global A13 concern/integrity failure, authorization/CAS/proof failure rejects the whole set.

Append required line revisions, advance affected heads, insert immutable ordered manifest/one set receipt, required per-line audits and one set audit, and increment Project row version exactly once. Circular revision/member/receipt references, if used, require explicitly deferred same-transaction constraints, never an independently committed placeholder. Flush, construct the post-write shared snapshot/token with expected own effects, and register the final outer-commit check against that **post-write** state. Do not compare post-write state with the old input CAS and reject the command's own increments.

Immediately before outer commit, re-resolve active actor/org/grants/session, DRAFT, full selected closure, source generation/verified bytes, basis/deviation state and exact retained/new heads under held locks. Recheck current UTC after waits/flush, not transaction-start time: `effective_at <= now < min(review_due_at, expires_at if present)`. Validate no intervening dependency change, including the exact prepared tuples, and perform no further long-running work before commit. A failure rolls back every revision/head/receipt/manifest/audit/Project increment, including earlier valid rows. No partial response is success. Deadlock/serialization/timeout before known rollback is a whole-set no-write failure; ambiguous transport remains uncertain.

This is an observation-based linearization boundary for external bytes: PostgreSQL protects database rows, not physical storage after verification. Verify every unique selected retained source before and at the final boundary using bounded before/read-verified/after evidence; a later loss/expiry makes a subsequent read non-current while the receipt remains a truthful historical commit. Do not claim atomically locking a remote filesystem or detecting an outage that no participating observer saw. Such stronger physical guarantees are not assumed by A13 or this ADR.

Diagnostics discovered inside the professional transaction are captured as typed proof candidates only. On rejection, roll back professional work first, then invoke §7 in separate bounded transactions against still-current exact heads. No selection-success receipt/audit survives rejection. On success, return/reconcile the immutable professional receipt even if a subsequent diagnostic fails; separately mark current projection unavailable and lock further writes. Never pretend an already committed selection rolled back because its post-commit projection failed.

### 6.3 Authenticated access, replay and minimized audit

New positive/withdrawal writes require active authenticated same-tenant human, active org, existing `workbench:edit`, active owned Workbench session, DRAFT and exact CAS; session acquisition retains `workbench:open`. Existing `project:read` governs scoped preparation/history/source metadata. No new RBAC grants. AI/system/worker cannot choose, confirm or impersonate the professional. Server derives actor/tenant, enforces cookie/CSRF/origin controls and safe foreign-scope 404/denial. Denied reads clear protected client state.

UUID is retained before transport and globally unique; digest covers tenant/actor/Project/session/contract and the entire canonical invocation, including expected versions and all rows. Receipt lookup checks current access and exact scope before disclosure. Same UUID + identical invocation replays the original historical complete result map and post-commit context, without new head, audit, receipt or Project increment. Changed payload or actor/tenant/session scope conflicts safely. Mutation-route replay retains current active access/owned-session requirements; historical receipt GET uses current `project:read` and original-actor scope without requiring the old session to remain active or Project DRAFT. Replay does not require old candidates, CAS or Project status still valid, but requires intact historical receipt/journal proof. Current Case State is a separately labeled fresh result; a receipt never claims current COMPLETE.

After timeout/500/uncertain result, block new commands and recover the **original UUID receipt**. A missing receipt is not proof of no write and permits no blind new UUID. A definitive no-write 409 still reconciles original identity, reloads coherent preparation, and requires a new deliberate click; no automatic CAS replacement, auth replay or per-row retry. If recovery cannot establish outcome, remain uncertain rather than guessing. Receipt pages may be bounded, but the committed result is one complete immutable set, never a collection of partial successes.

Use proposed set event `NCC_SELECTION_SET_CONFIRMED`; line events `NCC_SELECTION_CONFIRMED`, `NCC_SELECTION_CHANGED`, `NCC_SELECTION_RECONFIRMED`, `NCC_SELECTION_WITHDRAWN`; diagnostic `NCC_SELECTION_MARKED_STALE`. Re-establishment uses CONFIRMED with bounded re-establish code. Retain emits no new line attestation. Every official event includes a `supplier_selection_v1` namespace/contract discriminator and successor receipt/fact identity, so reused event names cannot be mistaken for legacy provenance. Atomicity is one transaction, not one physical AuditEvent: the accepted A15 per-line plus set audits form one logical command outcome, and the fold verifies that exact one-to-many correspondence. Atomic audit allowlist: tenant/actor/system identity, Project/line/session/command/contract/receipt/fact IDs, predecessor/head/generation/pre-post versions, canonical request/content/proof digests and bounded reason/warning codes. Exclude money/quantity, names/tax/contact, source bytes/text/keys/paths/URLs, credentials, full manifests/payloads and freeform reasons. Those necessary protected snapshots live in scoped history, not public Case State or bulk audit.

## 7. Durable currentness observations and pure-provider boundary

### 7.1 Typed fault proof and sole writer

`SupplierSelectionInvalidationObservation` is an immutable technical fact, never a stored stage flag or professional choice. Target exact positive selection revision/head; allocate monotonically increasing **per-line** generation under Project lock, continuing across successors/tombstones. The head index's generation equals the fold's maximum. An observation remains attached to its original head; successor acknowledges previous generation but does not inherit an old target's fault as its own. Any intact observation targeting the current positive head permanently prevents currentness, even when dependency values/bytes later recover. Only explicit professional whole-set successor with fresh eligible proof can restore positive authority. Corrupt observation history cannot be waived by a successor.

Retain typed proof, not digest alone: schema/verifier version, trusted server observer identity, observation UUID/UTC, exact scope/target/head/generation at capture, expected dependency identities/values/digests, observed identities/versions/statuses, and deterministic reason. Source proof records before/verification/after status, expected/observed checksum and length, provider version/creation, head/revision/binding IDs and protected target digest. Database proof records authoritative old/observed scoped fact IDs/content/version and fold reason; expiry proof records exact deadlines and observed server UTC. Basis/deviation proof records pinned/current revision/generation and changed axes/target applicability without public commercial values.

Allowlisted causes: selected A13 confirmed authority superseded/withdrawn or no longer eligible; retained source absent/unavailable/integrity/generation/head mismatch; Supplier/currency/line/seal/upstream material binding change; deadline/effectiveness failure; Project basis change; applicable selected-item deviation change. Known global A13 concerns/integrity failures retain owning precedence and cannot be converted into a local harmless warning. Unprovable journal corruption is a global fail-closed state; do not mint a trusted per-head observation if target lineage itself cannot be proved. Generic software error is not an invented source-loss fact.

Propose sole internal `RecordSupplierSelectionInvalidation`, invoked only by trusted application observation orchestration with a typed proof produced by server-owned resolver/verifier. No public endpoint, RBAC grant, arbitrary client proof, source URL or freeform verdict. Use the system-principal category already distinguished by CODEX/guardrails, never fake human user/session/confirmation. This is conceptual authority, not a claim that current A13 has a system-actor admission or diagnostic receipt adapter: the future runtime prerequisite must implement and prove that narrow admission/audit contract without adding a human grant. The writer may append observation/technical receipt/minimized audit and update technical generation/Project version; it cannot change selection head/chosen item, withdraw, clear observations, mutate quotes/basis/deviations, create DocumentRevision or write final price. It is allowed in non-DRAFT strictly for diagnostic currentness; professional writes remain DRAFT-only.

Current `retained_source` returns `(proof, current)` and can catch exceptions without preserving a typed failure reason. Future prerequisite work must expose typed verified failure observations through the same bounded storage checks without changing A13 eligibility semantics. Known provider-unavailable results may prove availability loss; an uncategorized crash/timeout without verified scope/result yields UNAVAILABLE/error, not fabricated fault or positive COMPLETE. No new OCR/AI/source-content evaluation.

### 7.2 Bounded diagnostic transaction, dedup and recovery race

Close the caller's read/failed-command transaction before diagnostic persistence. For one captured fault, acquire Project first; revalidate server principal/scope, exact target head, expected Project/shared token, line/head/generation and proof provenance. Dedup fingerprint is canonical target revision + dependency identity + expected/observed authority generations/status/proof + reason; exclude observation time and transport attempt UUID so repeated identical faults deduplicate. Unique scoped fingerprint/target/reason plus unique command UUID prevents double generation allocation. Existing duplicate returns original historical receipt without writes after scope/integrity checks, even if target is now historical.

For a new observation require the target still be the exact current positive head; allocate generation +1, insert fact/receipt/audit and increment Project version once atomically. No independent nested commit. Audit failure rolls everything back. A captured verified fault remains valid if the source recovered before this diagnostic transaction: validate captured provenance/target, not that the outage is still happening. If a successor moved the head, reject the stale target and reobserve the new head; never attach old proof to it.

If only shared CAS/Project changes while the same target remains current, a **definite no-write** conflict permits the internal observer to refresh versions and resubmit the same captured fault using a new invocation UUID and unchanged observation identity/fingerprint. It must not discard the fault in favor of a now-healthy read. Unknown outcomes first reconcile original diagnostic receipt. Limit each fault to one such refreshed retry per coordinator pass; contention returns UNAVAILABLE/reload, not an unbounded loop. This technical retry gives no professional command auto-retry authority.

Participating basis/deviation or dependency commands may ask the sole writer to append deterministic invalidations in their same caller-owned metadata transaction when the exact affected heads and changed facts are already locked/proved; no nested independent commit or duplicate Project increment is allowed. The enclosing command's single increment and atomic receipt/audit include technical observation identities. This transactional invocation is distinct from observation after a failed professional selection, which must occur only after rollback. External/read-detected faults always use the separate diagnostic transaction above. Future writer contracts must declare which boundary they use; no direct table insertion is allowed outside the sole writer.

### 7.3 `SupplierSelectionObservationCoordinator`

The application-level coordinator owns orchestration outside `resolve_authority`, A13/selection providers and `get_case_state_projection`. Those pure components only read supplied coherent facts/observations; they never dispatch a mutation or create a hidden write through autoflush. API routes delegate explicitly to the coordinator rather than insert diagnostics in a GET handler. This is a declared application read-path side effect newly proposed here, not a claim current A13 has it.

1. Authenticate `project:read`/tenant scope. Obtain one caller-owned repeatable-read snapshot, authoritative dependency fold and bounded trusted byte observations. Healthy reads and already-recorded faults perform no diagnostic write or Project write lock.
2. If new proved faults target current positive heads, retain typed proof and close the read transaction. Invoke bounded technical transactions in stable sealed-line/dependency order. Persist every fault needed before publishing its stale observation; a partially failed batch exposes no positive current/COMPLETE result.
3. Discard the old snapshot. Re-read one coherent post-observation snapshot through the same pure registry/projector. Return its Project row version/shared v7 token to preparation and Case State, never the pre-increment token.
4. Perform at most one fresh observation pass on this snapshot. If another new fault/change cannot be reconciled within the bounded pass/retry budget, return UNAVAILABLE/error and reload-required. Do not publish mixed-era COMPLETE or loop indefinitely. Already proven BLOCKER concerns remain known blockers, never downgraded merely because no repair route exists.

All global Case State and selection preparation callers must use this seam; no alternate positive path bypasses observation persistence. Healthy projection is still one coherent read transaction as ADR 0036 requires. Diagnostic transactions are outside that projection, followed by a new coherent projection; no persisted stage row or second algorithm is introduced. A diagnostic write intentionally invalidates older prepared shared CAS. New preparation returns the post-observation token so it does not conflict with its own write.

If diagnostics cannot persist/audit, fail closed: no refreshed positive assertion and no new professional write based on unverified state. Historical committed receipts remain truthful and independently recoverable with current status unavailable. Persisted exact-head faults survive source recovery/restarts. A captured but uncommitted fault is never published as durably known; process-local latches, TTLs, best-effort jobs or hash-only tokens cannot replace the ordering barrier.

## 9. Case State v7, COMPLETE and product boundary

Propose one successor registry/provider: `supplier_selection_v1`, shared token `global-case-state-v7-supplier-selection-v1`, pending action `supplier_selection_prepare_required`, context `supplier_selection_preparation`, stage SUPPLIER_SELECTION. The positive predicate is:

```text
future selection capability separately accepted, implemented and certified
AND current upstream SUPPLIER_QUOTES COMPLETE with intact global authority
```
