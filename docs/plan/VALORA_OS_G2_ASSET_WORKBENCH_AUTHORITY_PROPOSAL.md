## 2. Preferred business meaning and fixed membership — A, B, C, D, K, M

After ASSET_REVIEW COMPLETE, the operator prepares the description of each already-authoritative asset for later evidence comparison, then explicitly confirms readiness of the whole exact set. The mandatory new facts are (1) every member's persisted description is a string of at most the existing 5,000-character bound with non-empty trimmed content, and (2) an immutable human readiness confirmation of those exact official inputs and current review proofs. Text presence is machine-checkable; adequacy of the description for this bounded preparation purpose is the human's attestation. No classifier, mandatory taxonomy/identity match, structured specification schema or independent quality approval is invented.

| Stage | Business authority / distinguishing fact |
| --- | --- |
| ASSET_REVIEW | This exact sealed set is structurally valid and each member has a current human acceptance; it does not require descriptions or any price to exist. |
| ASSET_WORKBENCH, proposed | Descriptions of every sealed asset are officially prepared and one human confirms the current whole set is ready for the next separately authorized evidence task. This is not a second per-line acceptance. |
| PRICE_EVIDENCE | Later independently accepted source/evidence and price-rationale decisions; no evidence adequacy is attested here. |
| APPRAISAL_RESULT | Later authoritative final appraisal decisions/result suitable for a document DataSnapshot; no Workbench field or readiness receipt substitutes for it. |

**Membership:** preserve exactly ADR 0048's non-empty sealed correspondence, seal ID/digest, membership version and staging-row → line identities. Compare all official Project lines, never only a page/filter/selection. Add/delete/replace/unsealed manual lines remain out of scope. A future membership change needs a separate accepted command with versioned correspondence, invalidation, CAS, atomic audit, receipts/replay and Case State semantics. A rejected line is still a member and a blocker, not permission to drop it.

**Description:** recommend mandatory for this successor only, not because Human Commit happens to support it. Without a prepared asset description, the new stage would add no objective preparation fact beyond ASSET_REVIEW and risk becoming ceremonial duplicate acceptance. Existing nonblank official descriptions may qualify without forcing a new draft or edit. No magic sentinel, copied name or fabricated description is required/accepted by an automated rule; semantic adequacy stays the confirming human's responsibility. The risk of perfunctory text must be tested in bounded product acceptance, not solved by AI approval.

**Appraised unit price:** OPTIONAL WORKING DATA. A present value is officially persisted through its existing bounded mutation route, but its business interpretation at this stage is provisional. Missing price never prevents Workbench completion; neither currency, quotes, supplier choice nor rationale becomes mandatory here. Present price still participates in ADR 0049's official-input validation and the readiness snapshot: a changed value invalidates an attestation of that snapshot. This is currentness, not a final-price requirement. Existing Human Commit positivity/Decimal rules are retained; this proposal does not relax them because the validation rule set also accepts some structural values. Later price/evidence, supplier and final appraisal commands must establish their own authoritative decisions; they cannot infer approval from this column or overwrite/rebind decisions automatically.

**Non-authoritative presentation:** session open, heartbeat, layout, panel state, grid view, selection, active row, drawer/tab, page visit and local React state never create, invalidate or restore completion. An active owned session is only an invocation/access prerequisite. Saved/local/stale drafts have no effect on official facts; the confirmation UI must explicitly describe that it confirms persisted values and warn about the actor's uncommitted work, without making absence of drafts a domain predicate.

Keep the four existing purposes separate: draft save ≠ official mutation; Human Commit = bounded official value mutation; ValidateProjectAssetLine = human-triggered deterministic validation; DecideProjectAssetLineReview = explicit human review. The proposed preparation command invokes none of them automatically and changes no restricted line field. Direct PATCH of description/appraised_unit_price/review_status/validation_status remains forbidden. Existing allowed non-restricted PATCH retains its own authority and invalidates proof currentness when its official inputs change.

## 3. Proposed explicit human confirmation and concurrency — E, N

**Choice: explicit human confirmation YES, with fact-derived read projection.** A deterministic read can prove descriptions exist; it cannot prove the professional deliberately finished preparing the set. Store the immutable human fact, then derive COMPLETE on every read from that fact's currentness. Never persist a mutable `stage_done`, cache stage truth or use WorkflowInstance.current_state. Confirmation is a readiness declaration, not final appraisal approval, publishing or a Project status transition.

Proposed command: `ConfirmProjectAssetWorkbench`, contract `asset-workbench-confirmation-v1`. Only an active authenticated human in the owning active organization, with effective existing `workbench:edit` and an active owned Workbench session for this Project, may invoke it. No AI/system/job caller or fabricated human confirmation. Project and tenant scope are server-resolved; cross-tenant/wrong-Project targets or session return safe 404 without leaking IDs. No new role grant or privileged bypass.

Strict proposed request, with extra fields rejected:

| Field | Exact proposed precondition |
| --- | --- |
| `contract_version` | Literal `asset-workbench-confirmation-v1` |
| `command_id` | UUID idempotency key, unique within authenticated tenant across this command family |
| `confirm` | Strict literal `true` |
| `expected_project_row_version` | Strict positive integer; exact locked Project row version |
| `expected_case_version` | Current shared opaque 64-character lowercase SHA-256 token |
| `expected_seal_id` / `expected_authoritative_set_sha256` / `expected_membership_version` | UUID / lowercase SHA-256 / strict positive integer; exact current seal and whole set |
| `expected_line_versions` | Complete, duplicate-free list of `{line_id:UUID, row_version:positive strict integer}` for every member, exactly equal to locked rows; no partial/current-page list |
| `supersedes_confirmation_id` | UUID or explicit null; exact latest historical confirmation if replacing one |
| `reason_note` | Null for first confirmation; trimmed nonblank string ≤2,000 Unicode characters when superseding a prior confirmation; protected record only |

The request contains no proposed values, client-selected verdict, source/price/evidence decision or client-computed readiness digest. Authenticated actor, organization and active session identity are derived server-side and bound in persisted provenance; arbitrary actor/session spoofing is not accepted.

For every new confirmation, require Project DRAFT, current prefix/Official Intake, current guarded seal, exact non-empty membership/lineage, no scoped BLOCKING issue, all current ASSET_REVIEW accepted+valid proofs and all descriptions ready. The complete expected line-version list complements the shared CAS; it does not replace full-set proof resolution. A new command ID against an already-current confirmation is a same-state denial, not another receipt or success audit.

**Lock order and linearization:** tenant-scoped Project FOR UPDATE first → selected batch → ordered staging `(source_row_number,id)` → all ordered Project lines by UUID → present global reference rows FOR SHARE in Unit/Currency/Brand/Manufacturer and UUID order → scoped issues/proofs and this command's receipt/confirmation records in stable order. Reuse the existing authority resolver and canonical serializer, then lock/recheck active actor/organization/grants/session consistently with the existing line-command access boundary. All other official-input, issue, Project, seal and proof writers remain Project-first. Hold locks and authority checks through outer commit; never acquire Project after a child. Permission/session/reference changes must serialize or be rechecked so they cannot win between authorization and commit. Future runtime must prove this with actual PostgreSQL races in both orders.

Persist one append-only confirmation binding tenant/Project/actor/session, pinned preparation contract, seal/membership, exact canonical official-input/reference/rule digests, ordered member identities, latest validation generations and current positive human decisions, and invocation versions. Persist one bound receipt and exactly one `ProjectAssetWorkbenchConfirmed` audit, increment Project row_version once, and commit all together or roll back all. Do not modify lines, review/validation statuses, workflow state, membership, price decisions or issues. Canonical confirmation content digest excludes its own ID, post-write Project row_version and shared case token to avoid a self-invalidating proof.

**Shared CAS successor:** propose `global-case-state-v4-asset-workbench-confirmation-v1`, retaining every current v3 input and adding the preparation-contract digest and latest confirmation/reversal identities and digests, including explicit absence. Reuse the one canonical hash algorithm for snapshot reads and locked writes. Confirmation's own Project row increment changes CAS but not its content-currentness predicate. No implementation or silent mutation of v3 is authorized here.

**Audit allowlist:** command/receipt/confirmation IDs, contract, scoped Project/actor/session metadata, seal/membership identities, input/proof digests, old/new Project versions, expected tokens, confirmation=true, superseded/reversal IDs and reason-present flag. Keep descriptions, amounts, freeform notes, bulk line arrays, credentials, SQL, paths and stacks out of audit and route payloads. Protected immutable confirmation records retain the full ordered bindings required to verify coverage; audit alone is not their substitute. Any audit/sanitizer/flush/transaction failure rolls back confirmation, Project increment, receipt and audit. Denials produce zero command writes/audits; no new failure-audit engine is proposed.

**Replay and unknown outcome:** canonical receipt digest binds tenant, actor, Project, command contract and all strict request fields, including the exact expected versions and supersession. Fresh authenticated access/effective permission/owned-session checks precede any receipt disclosure. Exact UUID/content/scope replay returns the original receipt with zero writes/audits, even after DRAFT ends; mark it historical when no longer current. Reuse with different request/actor/Project conflicts. A receipt proves historical execution, never current COMPLETE. After timeout, reconcile scoped receipt + immutable confirmation + required atomic audit, then read fresh Case State. If absent with a proved non-commit, refresh all preconditions and explicitly reconfirm before a new UUID attempt. If ambiguous/corrupt, fail closed; no blind retry, Boolean repair or stale failure write.

**Supersession/reversal:** changed facts require a new explicitly confirmed snapshot with exact prior confirmation ID and reason; append the successor link and preserve old confirmation. To withdraw without changing values, propose separate bounded `WithdrawProjectAssetWorkbenchConfirmation` (`asset-workbench-withdrawal-v1`): same human/access/DRAFT/Project-first/full-set/CAS/receipt rules, strict confirm=true, exact current confirmation ID, mandatory reason, one append-only reversal, one Project row increment and one atomic `ProjectAssetWorkbenchConfirmationWithdrawn` audit. It never resets line review or prices. No automatic reversal on reads. Future runtime must implement withdrawal with confirmation, not leave an irrevocable or direct-delete shortcut. A new UUID repeat withdrawal conflicts; exact replay reconciles only its original receipt. A later reconfirmation links the latest withdrawn confirmation/reversal with fresh versions and reason. An explicit withdrawal makes the stage INCOMPLETE, not an unresolved stale attestation.

The strict withdrawal request uses `contract_version=asset-workbench-withdrawal-v1`, command_id, confirm=true, expected_project_row_version, expected_case_version, expected_seal_id, expected_authoritative_set_sha256, expected_membership_version and the full expected_line_versions list with the same types/exactness as the confirmation request; replace supersedes_confirmation_id with required `expected_confirmation_id:UUID` and require nonblank reason_note ≤2,000 characters. Reject extras. Withdrawal may target the latest non-withdrawn confirmation even when its content proofs are stale or review is unfinished/negative, provided ownership, DRAFT, exact current CAS/set/versions and coherent seal/lineage remain proved. It removes a readiness claim and cannot clear those independent impediments; denying withdrawal merely because readiness is no longer current would leave no bounded human reversal. Corrupt membership/lineage still denies the write and retains diagnostics.

Malformed contract/confirmation/versions/reason → sanitized 400; missing/inactive identity or denied effective permission → established 401/403; inaccessible scope/session → safe 404; new non-DRAFT write → sanitized 400; CAS/set/proof mismatch, same-state new request or UUID-content reuse → sanitized 409; technical failure → sanitized technical error, zero committed effects. No response discloses foreign identifiers or raw internal data.

## 4. Exact proposed stage predicate — F

All rows below are **future proposed behavior only**. Account-independent stage truth is computed from one tenant/Project snapshot, never from effective permission, session, client state, audit alone or cached status strings. Use only `NOT_AVAILABLE | BLOCKED | STALE | INCOMPLETE | COMPLETE`, in exactly this order:

| Precedence / result | Exact predicate after earlier rows fail |
| --- | --- |
| 1 — NOT_AVAILABLE | Successor authority/runtime/provider is absent or unwired, or no scoped committed Official Intake exists / the four mandatory prefix stages are not COMPLETE. Today this always applies to ASSET_WORKBENCH. An unavailable prerequisite gives no invented mutation/recovery route. |
| 2 — BLOCKED | An open known scoped Project/member BLOCKING issue; provable sealed membership divergence (extra/unlinked/missing/deleted/replaced member or empty set); current flagged/rejected human hold; current deterministic invalid proof; or Project not DRAFT while preparation is unfinished (the COMPLETE content/proof predicate below is not satisfied independently of status). Preserve authoritative upstream blocker diagnostics; stale proof strings alone cannot fabricate an invalid verdict. |
| 3 — STALE | No independent blocker, but immutable Intake/Result/source/mapping/staging/seal lineage is unproved/corrupt/mismatched; or a latest non-withdrawn historical Workbench confirmation exists whose preparation contract, official-input/reference/rule digests, exact membership or validation-generation/current-human-decision bindings no longer match the current snapshot. Retain all diagnostics, with deterministic first reason. |
| 4 — INCOMPLETE | Current coherent lineage and membership, no blocker/stale; ASSET_REVIEW lacks current full-set positive proof, or at least one official description is null/trimmed empty, or no non-withdrawn confirmation exists. Explicitly withdrawn confirmation counts as absent. Never-confirmed ordinary preparation and revalidation/review work are unfinished, not STALE. |
| 5 — COMPLETE | Exact current non-empty sealed membership; current full-set ASSET_REVIEW accepted+valid proofs; all official descriptions satisfy §2; one latest non-withdrawn immutable human confirmation with intact receipt/audit and exact §3 content/proof bindings; no blocker/stale. Derive on every read. A Project status change alone does not erase these facts. No price-presence, evidence, quotes, supplier, UI or draft condition. |

Malformed confirmation/receipt/audit linkage cannot yield COMPLETE; classify unprovable attestation as STALE, not missing ordinary work. An explicit absent/withdrawn fact is distinct from a corrupt referenced fact. Missing mandatory source/lineage never becomes Empty. Known independent blockers outrank STALE; preserve both diagnostics. Unknown issue target spellings/IDs do not leak foreign data or become invented blockers; known cross-scope authoritative corruption fails closed. Warnings remain separately visible and do not become BLOCKING issues.

The DRAFT distinction deliberately mirrors accepted ASSET_REVIEW: completed current facts remain COMPLETE outside DRAFT, but unfinished preparation needing a new official write is BLOCKED outside DRAFT. New confirmation and withdrawal always require DRAFT; historical receipt reconciliation never authorizes a non-DRAFT write. Obsolete Workbench snapshot confirmation is intentionally STALE for this proposed successor; upstream ADR 0049 input-proof obsolescence remains its accepted INCOMPLETE revalidation work. Publish both stage diagnostics without relabeling the upstream predicate.

## 5. Currentness and invalidation — G, D7

Content-currentness binds the existing ADR 0049 exact official-input fields (asset_name, description, quantity, unit_id, raw_price/currency, appraised_unit_price/currency, brand_id, manufacturer_id, line identity and lineage), canonical Decimal/null/string distinctions, present reference facts, immutable rule digest, seal/set and each latest validation generation/current positive decision. The human attests the current official asset snapshot, even when some working fields are optional.

| Change / condition | Effect on existing confirmation / future stage, after availability |
| --- | --- |
| Actual official description change, including removal | Old attestation non-current; STALE unless independent blocker. Human Commit still invalidates ADR 0049 input proofs; correct/validate/review then explicitly reconfirm. No direct status reset. |
| Actual official appraised_unit_price or any other covered official-input change | Same snapshot invalidation, even though price presence is optional. Old invalid/accepted strings are historical; no final appraisal inference. |
| Same canonical-value official write / unrelated row-version increment | CAS changes where existing writers increment it; no snapshot invalidation solely from row version. A stale submitted client token gives 409/reload, not a STALE fresh projection. |
| New committed validation generation, even identical verdict | Prior positive review no longer current; old Workbench confirmation STALE. Reaccept and reconfirm required; invalid outcome instead BLOCKED by higher precedence. |
| Human review supersession/reversal | New generation/decision binding invalidates old confirmation; flagged/rejected is BLOCKED and survives edits/revalidation; a later positive reversal still needs reconfirmation. |
| Membership divergence / line deletion or corrupt line ownership/correspondence | Provable missing/extra/replaced member: BLOCKED. Corrupt/unprovable seal without a proved membership violation: STALE. No command may repair or silently shrink the set. |
| Source/Result/Analysis/mapping/usage/lineage corruption | STALE unless independent blocker/availability prerequisite wins. Reload and diagnostic investigation only; no closed source/remap/Apply shortcut. |
| Reference fact or pinned rule/preparation-contract digest changes | Proof/attestation no longer matches; STALE for a prior confirmation, ordinary INCOMPLETE revalidation if never confirmed; current invalid verdict is BLOCKED. A rule/contract replacement requires separate accepted version authority. |
| Project leaves DRAFT | A content-current, otherwise unimpeded confirmation remains COMPLETE; unfinished preparation is BLOCKED because required new writes are forbidden. Status alone changes CAS/access, not readiness content. All new confirmation/withdrawal writes denied; historical receipt replay is a read. No status-change/return-to-DRAFT command is proposed. |
| Project later returns to DRAFT under separately accepted authority | Recompute from exact facts; unchanged content/proofs and non-withdrawn confirmation stay current. Previously blocked unfinished work becomes its ordinary INCOMPLETE or STALE condition. Row/status/token change alone is not an irrevocable invalidation epoch. Any changed bound fact requires reconfirmation. |
| Open scoped BLOCKING issue | BLOCKED; does not rewrite confirmation/review. Existing-authority resolution can restore COMPLETE if every bound fact is unchanged. Open WARNING changes CAS/diagnostics, not content-currentness. |
| Case State token change alone | Command preconditions become stale; reload. Do not compare confirmation's expected case token to the present token (confirmation itself changes it). Only a changed bound fact invalidates content; warnings/status/other facts can change CAS independently. |
| Draft save/delete/commit failure, page/session/layout/selection/heartbeat changes | No official snapshot change, no completion effect. A successful value commit changes authority only when covered canonical content changes. |
| Explicit withdrawal | Append-only human reversal; INCOMPLETE with intact history, not STALE. Never repair by deleting history. |

Reads only resolve/prove facts: no auto-validation, status reset, receipt, audit, workflow write or confirmation. No stored Case State/completion cache. Invocation row versions are concurrency/audit evidence, not self-invalidating content proofs.
