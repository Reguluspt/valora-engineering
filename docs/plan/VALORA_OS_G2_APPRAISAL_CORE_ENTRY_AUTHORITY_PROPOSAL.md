# OS-G2 A0 — Appraisal Core entry authority proposal

**Status:** Proposal for Product Owner and Gate Owner decision; no runtime or new domain authority is accepted by this file. **Baseline:** `main` at `81b5366d580681a768daaee6b7cacb54d1a8cc5e`, exact-main CI #530 SUCCESS. **Scope:** Official Intake → first official `ProjectAssetLine` set → `ASSET_REVIEW`; later OS-G2 stages are outside this proposal.

## Verified facts and gap

- The [roadmap](../VALORA_APPRAISAL_OS_UNIFIED_ROADMAP_V2_3.md) places `ASSET_REVIEW` first in OS-G2. The [PR-01 authority matrix](../implementation/VALORA_UIUX_V2_3_PR01_CASE_STATE_PROJECTION_CONTRACT.md) §§3–5 marks its completion predicate `UNMAPPED`; missing capability must be `NOT_AVAILABLE`, and blocking issues outrank ordinary actions. The [Orchestration Hub addendum](../design/VALORA_UIUX_HANDOFF_v2.3_CASE_OVERVIEW_ORCHESTRATION_BASELINE_ADDENDUM.md) requires one fact-derived primary Next Action and semantic route keys.
- `ProjectOfficialIntakeCommit` freezes the current Result identity/version/checksums, not asset lines. The [Intake service](../../backend/app/modules/project_master_data/application/official_intake_service.py) inserts no `ProjectAssetLine`; its [test](../../backend/tests/test_pr01_official_intake_service.py) asserts that Project status stays `DRAFT`. [G1.1K evidence](../implementation/G11K_PRECASE_PRODUCT_CLOSURE_E2E_EVIDENCE.md) ends with `NO_AUTHORIZED_DOWNSTREAM_ACTION`. The [current Case State provider](../../backend/app/modules/project_master_data/application/case_state_projection.py) leaves every downstream stage unavailable; this proposal does not claim otherwise.
- Confirmed mapping materialization owns S12-compatible staging but sets its batch to `parsed`; [staging validation](../../backend/app/modules/excel_import/application/validate_staging.py) must make it `ready_for_review`. [ADR 0029](../adr/0029-excel-staging-apply-command-and-lineage.md) and the [staging contract](../design/VALORA_EXCEL_IMPORT_STAGING_CONTRACT.md) §15 make human-confirmed, `DRAFT`-only S12 Apply the existing staging → official-line command. It appends one line per valid staged row, with unique staging-row lineage, atomic audit and `applied` batch state. Its [current handler](../../backend/app/modules/excel_import/application/apply_staging.py) checks project/batch/row readiness but does **not** check Intake, committed Result or selected mapping lineage. Thus the existing endpoint alone cannot certify *which* Pre-case batch becomes the initial official set.
- [ADR 0028](../adr/0028-official-mutation-command-and-atomic-audit-gate.md) requires exact-version, human-confirmed draft commit for restricted Workbench fields. Apply may create `description`, but spreadsheet appraisal price and review/validation decisions are excluded; new lines start `pending` / `unvalidated`. The [line model](../../backend/app/modules/project_master_data/models.py) has those statuses and `row_version`.
- A separate [manual line creation route](../../backend/app/api/projects.py) can create official lines with `project:update` and without S12 staging lineage. The current authorities do not say how such lines join the *initial* Pre-case-derived set; the proposed entry guard therefore treats pre-existing lines as a conflict pending explicit policy.

## Preferred contract — decision proposed, not implemented

Keep **S12 `ApplyProjectAssetImportBatch` as the sole authoritative staging promotion mutation**. Sequence on the same Project: current mapping materializes staging → Analysis/Result → **Official Intake commits** → staging validation/review as needed → human explicitly confirms **Apply** → official-line review through ADR 0028. Apply is a separate transaction strictly *after* Intake, never an automatic side effect of Intake or Result generation. Validation may have run earlier, but eligibility must be rechecked after Intake. Post-Intake **staging-only validation/re-validation** is proposed as an explicit ADR-ratified allowance; source upload and mapping mutations remain closed. Project must still be `DRAFT`.

Before this post-Intake Apply can be offered or executed, a **versioned server-side entry guard inside the sole Apply mutation path** must, under the established Project → batch → ordered staging lock order, prove all of the following or fail closed:

1. Exactly one same-tenant Intake commit identifies the immutable Result ID/version/checksums. The [Result lineage manifest](../../backend/app/modules/project_master_data/application/preliminary_result_service.py) identifies the same organization, Project, current batch, source artifact/generation/checksum, structure, confirmed mapping decision/digest, mapping `profile_usage_id`/digest and Analysis snapshot/digest. The Project's explicit current-batch pointer and mapping slot's `current_staging_usage_id` still match those identities; a historical or merely latest batch cannot qualify. The [immutable Analysis snapshot](../../backend/app/modules/project_master_data/application/preliminary_analysis_service.py) named by that manifest supplies the accepted source-row locator set, which must match the non-empty selected staging row set one-to-one; missing, extra or duplicate rows are a conflict.
2. The selected batch alone is `ready_for_review`, every staged row is `valid`, and counters agree under lock. A `parsed` batch needs validation first; `warning`, invalid, pending or zero rows cannot be partially Applied. No other batch may establish first entry. Pre-existing official lines fail closed until the Product Owner decides their treatment. An already Applied batch cannot be Applied again; matching created lines proceed to review. Existing Apply's append-only behavior is not silently turned into replace/upsert.
3. The human actor is active, tenant-scoped and has effective `workbench:edit`; the request presents the exact current entry/Case State version and explicit confirmation. A mismatch returns a safe conflict and refreshed projection, with no official mutation. These are proposed additional entry preconditions, **not** claims about the current `s12-pr-004-v1` request body.

This retains ADR 0029's one-line-per-row mapping, forbidden spreadsheet fields, no auto-Apply, append-only lineage, atomic rollback, `applied`/re-Apply `409`, and audit cardinality. It requires a **successor ADR to ADR 0029** before implementation: version the new Intake/lineage/expected-version guard and its denial/audit contract without weakening frozen v1 or leaving a bypass through its existing endpoint. The guard must be atomic with Apply, not a UI-only preflight. The ADR must specify any additional lock order and PostgreSQL race tests. Existing v1 re-Apply is a conflict, not an idempotent receipt: on an uncertain response, read batch/lines/audit before retrying; never assume a new request is safe.

## Candidate `ASSET_REVIEW` predicate

**Coverage unit:** every official line in the Project's authoritative entry set, with initial membership proved by a one-to-one Apply lineage from the committed Result's selected staging rows. No line may be omitted because it is off screen. Before an accepted policy for later manual/new-batch lines, extra or unlinked official rows invalidate the entry set rather than being silently ignored. Later authorized set changes must invalidate the previous completion proof. Completion requires **each** covered line's `review_status=accepted` and `validation_status=valid`; no appraised price is required at this stage. This is a proposed Product Owner choice, not an existing approved predicate.

| Candidate state | Proposed predicate (evaluate in this precedence) |
| --- | --- |
| `NOT_AVAILABLE` | No approved/wired `ASSET_REVIEW` provider, or Official Intake has not completed; expose distinct typed reasons `provider_unwired` and `official_intake_prerequisite`. Never infer completion from a later stage. |
| `BLOCKED` | After Intake: open same-project `BLOCKING` issue; zero/invalid/warning staging rows before Apply; pre-existing/unaccounted official lines; or a reviewed line explicitly `flagged`/`rejected` or `invalid`. Staging warning rows block **Apply** under ADR 0029; an ordinary open `WARNING` issue remains non-blocking. |
| `STALE` | After blocker precedence, committed Result/current-batch/source/selection/staging owner or official-set lineage conflicts with the proposed entry snapshot, including an unexpected selected-batch state outside `parsed`, recoverable `validation_failed`, `ready_for_review` or the exact matching `applied` batch. An old client version alone yields conflict/reload; a fresh authoritative read must recompute rather than remain stale forever. |
| `IN_PROGRESS` | Intake and lineage are current, but staging is `parsed` or recoverably `validation_failed` and needs validation, a `ready_for_review` batch needs human Apply, or the exact `applied` batch has official lines still `pending`/`unvalidated`/otherwise not accepted and valid. This is the business label; the existing wire result enum uses `INCOMPLETE` and needs a ratified mapping, not an unannounced API change. |
| `COMPLETE` | Non-empty exact entry set exists; every covered official line is `accepted` and `valid`; no open blocking issue or stale lineage; the proof is recomputed from current line versions and set membership. |

An open blocker outranks stale and ordinary pending actions; authoritative stale outranks otherwise valid progress. Unknown issue targets fail closed at the tenant/project boundary. `Project.status`, workflow enum, page visits, preliminary Analysis confirmations and Official Intake alone never make `ASSET_REVIEW` complete.

## Case State and one Next Action after Intake

Until the new provider and authority are accepted and wired, preserve the current `ASSET_REVIEW=NOT_AVAILABLE` and `NO_AUTHORIZED_DOWNSTREAM_ACTION` response. The current projection also caps `current_stage` at `OFFICIAL_INTAKE`; the accepted successor contract must extend that bound. **After** that gate, a successful Intake makes `OFFICIAL_INTAKE=COMPLETE` and the next current stage `ASSET_REVIEW`; the backend alone selects one primary action by blocker → stale → valid unfinished work → nearest required step. Proposed semantic route keys below are *not* current routes or frontend URLs:

| Fresh authoritative state | Proposed primary Next Action / typed context |
| --- | --- |
| Matching selected staging is `parsed` or recoverably `validation_failed` | `asset_import_validate_pending`; Project, Intake ID, batch ID, staging usage ID, exact case version and typed retry reason where applicable. |
| Same batch is `ready_for_review` with all valid rows | `asset_import_apply_confirm`; same typed context and expected version; explicit human confirmation required. |
| Exact batch is Applied; lines need review | `asset_review_line_pending`; Project, first deterministic pending line ID and line version. |
| Open blocking issue | Blocker action for the scoped issue ID/version takes precedence; no Apply CTA. |
| Applied line is `flagged`/`rejected`/`invalid` | `asset_review_line_blocked`; Project, first deterministic affected line ID/version and reason; route to human line review under ADR 0028, never auto-resolve. |
| Zero/invalid/warning staging rows, pre-existing/unaccounted official lines, or recovery needs closed Pre-case mutation | `BLOCKER` with typed reason and affected batch/line IDs where scoped; no unsafe Apply or disabled Pre-case route until a recovery contract is approved. |
| Lineage stale or current batch absent/ambiguous | Typed stale reason and involved authority IDs; no action route until the conflict is resolved by an approved recovery command. |

Warnings stay visible without becoming blockers. Resume may retain a still-valid line context but cannot override blocker/stale precedence. The future `case_version` must cover Intake/Result identity, batch/selection/validation/Apply generation, official-line membership and row versions, and scoped issue versions. Current [Case State schema](../../backend/app/modules/project_master_data/schemas.py) has `STALE` stage result but no `IN_PROGRESS` wire value or stale-specific Next Action kind; the successor Case State contract must settle those mappings and typed context before API/UI work.

## Controls, rejected alternatives and decision gate

- **Tenant/RBAC:** resolve Project, Intake, Result, batch, usage, staging, line and issue in one server-derived organization/Project scope; inaccessible cross-tenant objects return safe `404`. Keep Apply and restricted line commits behind `workbench:edit`; frontend visibility grants nothing. [G1.1K evidence](../implementation/G11K_PRECASE_PRODUCT_CLOSURE_E2E_EVIDENCE.md) records standard owner/appraiser grants, not a new role policy.
- **Concurrency/idempotency/audit:** preserve ADR 0029 Project → batch → staging locks, generation fingerprint, unique `source_staging_row_id`, all-or-nothing lines/lineage/batch/success audit, stale-failure suppression and safe failure payloads. Preserve ADR 0028 exact line `row_version`, human confirmation and atomic audit for restricted edits. The successor ADR must define atomic expected-version checks, new guard-denial audit cardinality and races with validation, another Apply, official-line creation/edit and Project status change; no raw cells or client secrets in audit.
- **Reject** Apply before Intake (official rows precede the official boundary), Intake auto-Apply or direct Result→line copy (bypasses human S12 mapping/validation/Apply), a second promotion command or direct SQL (duplicate mutation authority), naked v1 Apply on any ready batch (no committed-lineage gate), and completion from any single line, screen visit or `DRAFT` status (false project-wide completion).

**PRODUCT OWNER DECISION REQUIRED: YES. ADR ratchet required: YES.** The Product Owner must approve this after-Intake Apply guard, staging-only validation/re-validation after Intake, exact initial-set/per-line completion rule, pre-existing/manual/additional-batch policy and blocked/stale recovery semantics. Required separate follow-ups are: (1) accept the successor ADR 0029 ratchet and Case State predicate/Next Action contract; (2) implement the atomic Apply guard and ASSET_REVIEW provider with focused PostgreSQL lineage, tenant, version and concurrency tests; (3) add authorized UI routing and real-stack acceptance. This proposal authorizes none of those runtime slices or OS-G3 work.
