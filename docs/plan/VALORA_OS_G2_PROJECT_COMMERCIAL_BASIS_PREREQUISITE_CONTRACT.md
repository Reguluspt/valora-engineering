## 3. Facts, absence and immutable lifecycle

The professional declares exactly these three requested quotation inclusions:

| Field | Meaning of `true` / `false` | Future Vietnamese label |
| --- | --- | --- |
| `vat_included` | Requested quoted price includes / excludes VAT | `Bao gồm thuế GTGT (VAT)` |
| `transport_included` | Requested quoted price includes / excludes transport | `Bao gồm chi phí vận chuyển` |
| `installation_labor_included` | Requested quoted price includes / excludes installation labor | `Bao gồm nhân công lắp đặt` |

All are required strict JSON booleans on a positive declaration: missing, `null`, numbers and strings are rejected. No server/client/default/migration supplies `false`. Exactly three inclusion axes; no currency, warranty, payment or delivery-timing equivalence field is added to the basis. Existing Project fields remain ordinary Project metadata. These declarations describe what the appraiser requested, **not supplier-document confirmation, legal acceptance, a price conversion or an extra quote attestation**.

Canonical policy identifier: `project-commercial-basis-v1`. A positive immutable revision has all three values; first creation or authorized legacy establishment uses revision 1; later change appends revision `n+1` from exact `n`. Any boolean change is material. Establishing previously absent facts is material. Same three values under a new command UUID is a no-op and rejected; same original UUID replays its receipt. Reverting values creates a new revision and never erases history or revives an invalidated selection. No deletion, null-out, withdraw-to-UNKNOWN, in-place edit or non-DRAFT reversal is authorized.

| Resolved basis state | Meaning / read and consumer behavior |
| --- | --- |
| `KNOWN` | One intact current pointer to the terminal revision, complete chain and matching receipts/audits. Return all three booleans with exact identity. `false,false,false` is valid only when explicitly declared. |
| `UNKNOWN` | A legacy Project has **no** head, revisions or basis receipts; generation/revision number 0 and null revision ID. Return `declarations: null`, reason `legacy_basis_not_declared`. Absence is a scoped canonical fact, never negative values. |
| `UNAVAILABLE` | Contradictory/missing pointer, orphan revision/receipt, invalid digest/chain/audit, unsupported policy, foreign binding or incomplete proof. Never downgrade corruption to UNKNOWN or infer a head from maximum number. Fail closed and expose only a bounded diagnostic. |

No import, AI, Supplier text or historical fee can establish these facts. Legacy DRAFT Projects may acquire revision 1 only through the explicitly authorized human revise command below. Legacy non-DRAFT Projects remain UNKNOWN/read-only until a separately accepted non-DRAFT policy exists. Basis UNKNOWN makes automatic ranking UNRANKABLE under E1-B; it does **not** forbid deliberate future A13-eligible selection or invent an upstream intake/quotation COMPLETE gate. There is no stored `basis_complete` business-stage flag.

## 4. Proposed physical persistence and integrity

Use additive PostgreSQL tables. Names are proposed, with UUID IDs, native booleans, integer revisions and `timestamptz` server UTC. No JSON copy of booleans on `projects` and no mutable boolean authority alongside the journal. Scalar identities are indexed; JSON is limited to strictly typed immutable request/result/proof snapshots needed for digest/recovery.

| Proposed table / record | Physical columns and constraints |
| --- | --- |
| `project_commercial_basis_revisions` / `ProjectCommercialBasisRevision` | `id uuid PK`; non-null `organization_id`, `project_id`, `revision_number integer CHECK >0`, `policy_version varchar(64)`, three `boolean NOT NULL` with **no defaults**, `actor_user_id`, `command_id`, `receipt_id`, `audit_id`, `created_at timestamptz`, `content_sha256 char(64)`; nullable `predecessor_id`, `session_id`. `origin varchar(32)` in `project_create`, `legacy_establishment`, `revision`. Unique `(org,project,id)`, `(org,project,revision_number)`, `(org,project,id,revision_number)`, `receipt_id`, `command_id`; partial unique `(org,project,predecessor_id)` where predecessor non-null. Revision 1 iff predecessor null; origin create/legacy iff revision 1; create iff session null. Composite predecessor FK `(org,project,predecessor_id)` to same journal. |
| `project_commercial_basis_heads` / `ProjectCommercialBasisCurrentHead` | PK `(organization_id,project_id)`; non-null `revision_id`, `revision_number integer >0`, `head_version integer >0`. Composite FK `(org,project,revision_id,revision_number)` to revision. In v1, `head_version = revision_number`; start 1 and advance by exactly 1. Absent legacy row represents generation 0. A head is a mutable index, never independent authority. |
| `project_commercial_basis_receipts` / `ProjectCommercialBasisReceipt` | `id uuid PK`; globally unique `command_id uuid` across tenants and both basis command kinds; non-null org/Project/actor, `contract_version varchar(64)`, `request_sha256 char(64)`, typed `request_snapshot jsonb`, `result_snapshot jsonb`, `result_sha256 char(64)`, `created_at timestamptz`, `revision_id`, `basis_audit_id`, `post_project_row_version integer >0`, `post_head_version integer >0`; nullable `session_id`, `create_audit_id`, input Project/shared-CAS fields. New create requires null input Project/CAS/session and non-null create audit; revise requires exact non-null input Project/CAS/session and null create audit. Scoped unique `(org,project,id)` and `(org,project,post_project_row_version)`; result links exactly one new revision. |

Here `org` abbreviates the physical column `organization_id`; `project` abbreviates `project_id`. All three tables carry composite `(organization_id,project_id) → projects(organization_id,id)` FKs and delete RESTRICT. Revisions and receipts carry `(organization_id,actor_user_id) → users(organization_id,id)`. For non-null sessions, `(project_id,actor_user_id,session_id) → workbench_sessions(project_id,user_id,id)` uses its existing scoped unique key; tenant follows the Project/actor FKs. Check constraints explicitly govern nullable create versus revise session cases, because a composite FK alone skips nullable keys.

Receipt↔revision scoped references are DEFERRABLE INITIALLY DEFERRED within the same transaction; allocate IDs before insertion, never commit an incomplete receipt reservation. Include actor, command, session and contract agreement in a deferred consistency trigger/canonical fold; nullable create session must use null-safe equality. Audit IDs reference `audit_events.id` RESTRICT. Because AuditEvent lacks a composite scope key, a deferred constraint trigger verifies referenced audit tenant/actor/entity/command/event and allowlisted payload; the canonical fold independently verifies the same relationship. A plain audit ID FK alone is insufficient. Future schema review must show exact DDL and SQL-negative proof for these constraints, not merely ORM checks.

Use database UPDATE/DELETE rejection triggers plus ORM guards for revisions and receipts, including protection from cascade delete. Head updates require the exact successor/predecessor, `head_version+1`, matching scope and an intact command receipt; reject head DELETE and rewind. Deferred consistency checks require contiguous revision numbers, predecessor number `n-1`, unique terminal head and one matching immutable receipt/audit set for every revision. At writer cutover, a deferred constraint trigger on new Project INSERT requires revision/head 1, create receipt and both audits before commit; it does not fire retroactively on old rows or turn an ordinary legacy Project UPDATE into a mandatory declaration. This distinguishes legacy absence without trusting a timestamp and closes alternate-create bypasses. Existing `AuditEvent` history used by this contract must retain its append-only protection. Application roles must not disable triggers; maintenance recovery is outside this command scope. No repair-by-successor when history is corrupt.

### Canonical digests

Reuse the existing canonical JSON convention: UTF-8, sorted keys, compact separators, no NaN, lowercase hyphenated UUIDs; strict booleans, exact integers; UTC timestamps normalized to six fractional digits and `Z`; no floating values in basis facts. SHA-256 is lowercase 64 hex with syntax checks. Canonical schemas are versioned; unsupported versions fail closed.

- `content_sha256` hashes a typed `project-commercial-basis-v1` revision object containing org/Project/revision ID/number, predecessor ID, policy, the three declarations, origin, actor/session, command/receipt/audit IDs and timestamp. Exclude the digest itself; no recursively embedded receipt/audit hashes.
- `request_sha256` hashes authenticated org/actor, command kind/contract and the entire validated normalized request, including command UUID, all requested Project-create fields or all revise expected tokens/session/basis identity and values. Create excludes the server-generated Project ID because it is not yet an invocation input; the receipt binds that resulting ID immutably. Existing fee normalization remains its existing bounded Project concern, not commercial-basis money authority; serialize its validated database value deterministically for replay, never hash transport float spelling.
- `result_sha256` hashes the immutable result snapshot with resulting Project ID/version, revision identity/number/digest, head version, audit IDs, command/receipt identity, commit timestamp and any integrated A20 observation references. The post-commit live Case State token is not embedded in this hash: shared Case State includes receipt proof, so embedding its resulting token would create a digest cycle.

Store exact normalized request/result snapshots only in protected receipt history. Audit records carry IDs/digests/codes, not those snapshots. The fold checks digest recomputation, exact scalar/snapshot equality, all scoped references, chain/head continuity and exact audit correspondence. A digest is integrity evidence, not authorization, encryption or proof of supplier agreement.

## 5. Atomic CreateProject contract

Proposed command contract: `project-create-with-commercial-basis-v1`, exposed through the existing `POST /api/v1/projects` in a separately authorized coordinated API/client cutover. Request retains existing ProjectCreate fields and adds required `command_id: UUID`, `contract_version` and `commercial_basis` containing exactly the three booleans. Reject client tenant/actor/Project ID, session, current pointer, revision/digest, status and audit/receipt fields. Do not turn missing legacy-client fields into defaults or create an unversioned bypass endpoint.

Creation requires active authenticated same-tenant **human**, active organization, current `project:create`, existing cookie/CSRF/origin protections and normal Project field/reference validation. It does **not** require `project:update`, `workbench:edit`, `workbench:open`, a Workbench session, an existing Project version, intake/seal, A13 COMPLETE or a Case State input token. The client already makes one explicit Create action; no separate basis approval click is added.

Future transaction sequence:

1. Validate the strict typed request and derive tenant/actor server-side. Probe receipt by command UUID only after active admission; disclose/replay only exact actor/tenant/request scope. This precedes duplicate-code handling so a successful retry can recover its Project.
2. For a new command, start/use one owned transaction. Allocate private Project/revision/receipt/audit IDs. There is no existing Project to lock: insert the new DRAFT Project in this transaction, establish its initial row version 1, then admit and lock current actor/org/grants and validate/lock referenced master data in deterministic order. The new row is unobservable to other transactions until commit. Preserve exact existing code uniqueness semantics; the database unique constraint, not its precheck, decides simultaneous creates. Do not later request another existing Project lock while holding shared dependency locks.
3. Revalidate customer tenant/active status, signer tenant and global Currency existence at the commit boundary; preserve existing rules without inventing new grants or business requirements. Validate reference IDs before insertion for safe errors and revalidate protected rows after acquisition; FK errors/uniqueness races roll back the entire command. Creation's no-existing-Project exception must be reconciled with A20 multi-Project identity admission before selection integration, not implemented as a reverse lock order.
4. Insert revision 1 (`origin=project_create`, no session), head 1, complete immutable receipt, existing `ProjectCreated` audit with a minimized contract payload, and `ProjectCommercialBasisDeclared` audit. Both audits link the same command/receipt; they are two physical events in one atomic outcome. Do not increment Project a second time just to add its separate head row.
5. Flush, verify deferred bindings, revalidate active human/org/grants and reference state after waits, and commit once. Any validation/FK/receipt/audit/final-check failure rolls back Project plus all basis effects. A post-commit refresh or transport failure cannot undo the commit; report uncertainty and recover the original receipt.

The unique command UUID constraint arbitrates duplicate in-flight creation. On a uniqueness conflict, roll back before fresh secure receipt lookup; identical committed invocation replays, changed scope/payload returns bounded 409 without disclosing the owner. If code conflict belongs to another command, return definite no-write duplicate-code 409. Do not convert arbitrary integrity errors into replay success. If another transaction is still unresolved and no intact receipt is visible, outcome remains uncertain; no blind new UUID or second Project creation.

First success is 201 with a versioned envelope: `{contract_version, command_id, receipt_id, historical_result, replayed:false, current_context}`. `historical_result` contains the committed `ProjectResponse` snapshot, basis revision identity/declarations/digest and audit IDs; replay returns the same immutable result with `replayed:true` and 200. `current_context` is separately read after commit and may contain current Project version/shared case token/current basis or `{state:"UNAVAILABLE", reason_code:"reload_required"}`. It never changes the historical receipt or converts a committed create into a rollback claim. No create input token is manufactured from that output.

## 7. Secure reads, replay, uncertainty and minimized audit

Proposed reads: `GET /api/v1/projects/{id}/commercial-basis` for coherent current basis plus Project/shared-CAS context; `GET .../commercial-basis/revisions` for cursor-paged protected immutable history; `GET .../commercial-basis/receipts/{command_id}` for original-actor historical recovery. A create response may be lost before the client knows Project ID, so also provide `GET /api/v1/projects/creation-receipts/{command_id}`. Register that static route before generic ID matching and enforce current active human/org and existing `project:create`, original actor/tenant and create contract scope. It is narrowly the creator's own prior create result, not a Project enumeration or new broad read grant. It uses no Workbench session.

Ordinary current/history and Project-scoped receipt reads require current `project:read` and tenant scope. Receipt recovery additionally requires the original actor; administrators receive no implicit cross-actor receipt access. Do not require an old session to remain active or Project DRAFT for historical GET. Mutation-route replay requires the command's current mutation permission and, for revise, its exact still-active owned session; after those checks, an intact identical receipt replays before stale CAS/no-op/non-DRAFT rejection. Lost old-session access therefore uses authorized historical GET, never a forged replacement session.

Foreign/missing Project/revision/receipt yields a non-enumerating 404 after authenticated scope checks; permission denial yields safe 403; unauthenticated/expired access yields 401. No receipt existence, actor, digest or Project ID leaks through a reused UUID in another tenant. Current/history reads work outside DRAFT; protected data is cleared on 401/403/404. Server applies cookie/CSRF/origin policy to commands. AI/system/worker principals cannot declare or revise basis.

All current basis/context fields come from one caller-owned PostgreSQL REPEATABLE READ snapshot using the pure shared resolver; no hidden autoflush, head repair or diagnostic mutation. History pages cannot masquerade as full-chain integrity proof: the server validates the required chain/receipt/audit closure independently. A19 gets the same resolver data, not a second SELECT algorithm. Public Case State may expose bounded basis availability/reason and IDs/digests where allowed, never booleans, names, fees, receipt payloads or protected provenance as an expanded public context.

| Outcome | Client / server recovery |
| --- | --- |
| Same UUID and exact authenticated invocation | One immutable historical result; zero new revision/head/audit/receipt/version increments. Snapshot/digest equality covers all expected tokens, not only the booleans. |
| Same UUID with changed values, CAS, session, actor or tenant | Safe 409 `commercial_basis_command_reuse_conflict`; no effects and no foreign result. |
| Definite no-write CAS/no-op/status/validation conflict | Reconcile original identity as needed, reload coherent basis/context, let human review again; only a new deliberate action gets a new UUID. No automatic CAS refresh/replay. |
| Timeout, connection loss, 500 or post-commit serialization failure | Preserve original UUID/request and block further submit. Recover original receipt with current access; not-found alone does not prove rollback. After a server-established terminal rollback, the unchanged original invocation may be retried; a revised invocation needs new deliberate action. |
| Receipt/history proof corrupt or current context unavailable | No invented success/currentness. Intact historical receipt may still be returned independently when only fresh Case State is unavailable; otherwise remain uncertain and escalate integrity recovery outside this command. |

Required audit events: `ProjectCreated` plus `ProjectCommercialBasisDeclared` for new Project; exactly one declaration or revision event for later metadata command; A20 technical observations, if activated, add their required minimized events atomically. Include namespace `project-commercial-basis-v1`, org/actor, Project/session/command/receipt/revision/predecessor IDs, revision/head/pre-post Project versions, content/request/result digests and bounded origin/reason codes. Audit payload excludes all three commercial values, Project code/name/customer/fees, Supplier data, source bytes/text/keys/paths/URLs, raw requests/results, arbitrary free text, tokens and credentials. Those allowed protected facts remain only in scoped domain/receipt history. Historical `ProjectCreated` audit records are not rewritten. Verify exact event count, namespace, linkage and payload allowlist; sanitizer success alone is not proof.

## 8. Exact A19 consumer contract and shared currentness

Name the internal read contract `project-commercial-basis-reference-v1`. It is a typed server-owned value, not client attestation and not a new public ranking endpoint. `resolve_project_commercial_basis` accepts authenticated org/Project and the caller's coherent authority snapshot/transaction; returns:

| Field | Type / invariant |
| --- | --- |
| `contract_version`, `organization_id`, `project_id` | Exact reference version and scoped UUIDs. |
| `state`, `reason_code` | KNOWN / UNKNOWN / UNAVAILABLE with bounded reason; corruption distinguishable from legitimate absence. |
| `policy_version` | `project-commercial-basis-v1` for KNOWN; null for absent/unsupported state. |
| `revision_id`, `revision_number`, `head_version`, `content_sha256` | Exact current tuple for KNOWN; null/0/0/null for UNKNOWN; no usable authority tuple for UNAVAILABLE. |
| `declarations` | Exactly three booleans for KNOWN; null otherwise. |
| `authority_fingerprint` | Digest of version, org/Project, state/reason, policy and exact revision/head/content tuple; UNKNOWN uses the explicit `legacy-absent-v1` marker. Never just a hash of the three values. |

The fingerprint excludes `case_version` and Project row version; the shared resolver adds a canonical `project_commercial_basis_v1:<fingerprint>` input alongside existing facts. No hash cycle, wall-clock tick, independent token or stored completion bit. Basis revision, head movement, corruption or absence→known changes the shared token. Unrelated Project version changes can conflict an invocation without material-staling an otherwise intact selected choice.

**A19 binding:** deviation facts pin `(organization_id, project_id, basis_revision_id, basis_revision_number, policy_version, content_sha256)` at observation and name affected axes plus actual discovered inclusion values. Initial negative observation requires an intact KNOWN referenced basis and at least one real difference; UNKNOWN cannot support a fabricated difference-to-false. Revalidating current quote eligibility/ranking with UNKNOWN remains UNRANKABLE and may allow deliberate eligible selection per E1-B. A19 must define a truthful unavailable/establish-basis next step when an initial deviation lacks a reference; it must not create an affirmative compliance row.

Within the same exact quote revision, retained actual inclusion facts are compared against the current KNOWN booleans. A changed basis does not erase a known deviation or its observation reference; it may make actual values match for fresh ranking. Quote successor/correction/replacement continuity, exact effective item/line scope, targeted correction/clear and ambiguous lineage handling belong to A19, preserving ADR 0051 §3.2. Unsupported/ambiguous applicable lineage fails ranking closed. No rewrite of A13 `QuoteTerms`, original fact/digest/confirmation receipt, source or price; no mandatory positive per-quote checklist/upload/click. Warranty/payment/delivery timing remain outside the three axes.

## 9. Concurrency and participating writers

Use real PostgreSQL row locks and uniqueness/deferred integrity constraints, not in-memory mutexes. Existing-Project commands lock Project first. Reads use coherent snapshots; write transactions reload after lock waits, keep deterministic order and validate before outer commit. Proposed lock wait and outer command bounds follow ADR 0051 §8.3 (5 seconds / 15 seconds); no loop, chunked basis commit or partial observation success. A definite deadlock/serialization rollback is no-write; an uncertain transport result still requires original receipt recovery.

| Race / writer | Required serialization result |
| --- | --- |
| Two creates, same tenant/code, different UUID | Database unique code picks one; loser rolls back its Project/revision/receipt/audits. Same code in different tenants remains allowed. |
| Two creates, identical UUID/request | One complete Project/outcome; other returns original receipt after wait/rollback. Same UUID/different code/payload/actor is a reuse conflict, never a second Project. |
| Two revisions or two legacy establishments | Project lock, exact Project/shared/basis CAS and unique chain/head select one; loser has no effects. Disjoint boolean edits are not merged automatically. |
| Create versus earliest revise | Until commit no Project/session/basis is visible. After commit, revise needs a legitimately acquired owned session and exact returned/current tokens. No session-dependent create cycle. |
| Revise versus PATCH/archive/cancel | Existing Project-first writers serialize. Other writer first → old revision CAS or DRAFT check fails. Revise first → its truthful receipt survives; later metadata/status write cannot alter basis history. PATCH-only token changes are not material basis changes. |
| Revise versus preliminary/intake/line/A13 commands | Shared Project lock/token picks one reviewed invocation. Do not require unrelated upstream COMPLETE just to repair basis. No pre-change command may pass by using a separately computed token. |
| Basis versus A19 deviation write | Same Project/shared CAS before basis/deviation indexes; earlier change forces later command to reload exact reference and applicability. Existing deviation remains attached to historical observation basis. |
| Basis versus future selection confirm/withdraw | Basis first → prepared selection CAS fails. Selection first → material basis command atomically records sticky invalidation against all affected positive heads. Tombstones/history are not positive targets; no old-head observation attached to successor. |
| Basis versus A20 diagnostic writer | Compatible Project-first order; one shared Project increment for inline hook. Separate diagnostic first conflicts old input; basis first changes token/target proofs. No child→Project acquisition or own-token conflict. |
| Admission revocation/reference changes | Read/admission locks and final checks protect active user/org/grants/session and scoped references. Runtime must inventory permission, session, Customer, signer and Currency writers; prove both orders or stop for bounded integration authority. |
| Multi-Project Supplier/Currency/document/line writers | A20 owns complete integration/phantom admission inventory under ADR 0051 §8; stable Project order before shared rows and rollback/restart on newly discovered earlier Project. A18 does not claim existing writers repaired or authorize those changes. |

Do not hold a shared master-data lock and later acquire an existing Project lock. Creation is special only because its Project is newly allocated/uncommitted; it may not use that exception to mutate a second Project. Reference races and A20 new-Project/identity admission are explicit runtime DoR proofs, not hidden assumptions of this design.

## 10. Migration, compatibility and rollback strategy

No migration is delivered by A18. A later task must identify the then-current single Alembic head and author additive upgrade/deferred constraints/immutability triggers with real PostgreSQL proof. Do not hard-code today's migration head into a future runtime authorization.

1. Expand with empty basis revision/head/receipt tables, indexes, scoped/deferred constraints and guards. Preserve existing Project/A13/ADR0039 rows and audit bytes. No boolean columns/defaults, fabricated revisions, historical receipt fabrication or automatic backfill.
2. Deploy compatible reads that distinguish absent legacy state. Old server instances must be drained before enforcing the new create contract; a controlled writer cutover covers every Project-create route/job. Do not permit old split-commit creates concurrently with the new promise of mandatory declarations. Track deployment cutover evidence externally; it cannot be inferred from Project timestamps.
3. 5. Certify A19/A20/writer integration before any official selection/v7 activation. A basis-only prerequisite release does not certify them or APPRAISAL_RESULT.

Empty-table downgrade/re-upgrade may remove the additive structures in an isolated test only. Populated downgrade refuses destructive removal. Operational rollback must retain journal/receipts/audits and either use a compatible reader/writer version or hold new create/revise writes; never re-enable the old create API to manufacture missing facts after cutover. Backup/restore recovery needs a separately reviewed retention plan, tenant integrity and exact historical parity. No mass UPDATE/DELETE or cascade cleanup is a rollback mechanism.
